## ไอเดียในหนึ่งประโยค

configuration ของ Terraform ทุกส่วนคือ **block** เขียนด้วย HCL — `terraform`, `provider`, `resource` และ `data` คือสี่ตัวที่คุณจะเขียนบ่อยที่สุด รวมกันแล้วสี่ตัวนี้บอก Terraform ว่าต้องโหลด plugin อะไร คุยกับ GCP ยังไง ต้องสร้างอะไร และต้องอ่านอะไร

## HCL block syntax

HCL (HashiCorp Configuration Language) สร้างจาก block รูปแบบทั่วไปคือ block type ตามด้วย label ที่ครอบด้วยเครื่องหมายคำพูดศูนย์ตัวขึ้นไป แล้วปิดท้ายด้วย body ของ argument ใน `{}`

```hcl
block_type "label1" "label2" {
  argument = value
}
```

อย่าง `resource` block มี label สองตัว ส่วน `provider` block มี label ตัวเดียว comment ใช้ `#` หรือ `//` สำหรับบรรทัดเดียว และ `/* */` สำหรับหลายบรรทัด string รองรับ interpolation ด้วย `${...}` แต่ถ้าอ้างอิงค่าอื่นตรง ๆ (`name = google_storage_bucket.reports.name`) ไม่ต้องครอบด้วย `${}` — syntax แบบนั้นใช้เฉพาะตอนอยู่ข้างใน string ที่ยาวกว่านั้น

```hcl
# A single-line comment.
// Also a single-line comment.

resource "google_storage_bucket" "reports" {
  name = "acme-monthly-reports-${var.environment}" # interpolation inside a string
}
```

## terraform block กับ provider block

`terraform` block คือการตั้งค่า Terraform เอง ว่า Terraform เวอร์ชันไหนรัน configuration นี้ได้ และต้องใช้ provider อะไรบ้าง รวมถึงแต่ละ provider มาจากไหนและเวอร์ชันไหนที่รับได้

```hcl
terraform {
  required_version = ">= 1.11.0"

  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 8.0"
    }
  }
}
```

`source` คือ registry address ของ provider (`hashicorp/google` ชี้ไปที่ Google Cloud provider ตัวจริงบน Terraform Registry) ส่วน `version` เป็น constraint ไม่ใช่การ pin ตายตัว — `~> 8.0` อนุญาตทุก release ในสาย `8.x`

จากนั้น `provider` block ตั้งค่า instance หนึ่งของ provider ที่ประกาศไว้ด้านบน สำหรับ GCP ตรงนี้คือที่อยู่ของ project กับ region (และในโปรเจกต์จริง ๆ ก็มีเรื่องอย่าง credential ด้วย)

```hcl
provider "google" {
  project = "acme-app"
  region  = "us-central1"
}
```

## resource block: สอง label ที่มีความหมาย

`resource` block คือวิธีบอก Terraform ว่า "สิ่งนี้ควรมีอยู่" resource block มี label สองตัวเสมอ

```hcl
resource "google_compute_instance" "web" {
  name         = "web-vm"
  machine_type = "e2-medium"
  zone         = "us-central1-a"

  boot_disk {
    initialize_params {
      image = "debian-cloud/debian-12"
    }
  }

  network_interface {
    network = "default"
  }
}
```

- label แรก `google_compute_instance` คือ **type** ของ resource ถูกกำหนดโดย provider และเป็นตัวตัดสินว่า argument ไหนใช้ได้ และ GCP API ตัวไหนที่ Terraform จะเรียก
- label ที่สอง `web` คือ **name** ที่คุณเลือกเอง มีความหมายแค่ภายใน configuration นี้เท่านั้น

รวมกันแล้วทั้งสองตัวคือ **address** ของ resource นั้น คือ `google_compute_instance.web` ที่ใช้อ้างอิง attribute ของ resource นี้จากที่ไหนก็ได้ใน configuration ของคุณ เช่น `google_compute_instance.web.id` หรือ `google_compute_instance.web.self_link`

## data block: อ่านโดยไม่เป็นเจ้าของ

`data` block อ่านข้อมูลของสิ่งที่มีอยู่แล้ว คือ infrastructure ที่ configuration นี้ไม่ได้จัดการและจะไม่มีวันสร้าง อัปเดต หรือลบ นี่คือ read-only lookup ของ Terraform

```hcl
data "google_compute_image" "debian" {
  family  = "debian-12"
  project = "debian-cloud"
}

resource "google_compute_instance" "web" {
  name         = "web-vm"
  machine_type = "e2-medium"
  zone         = "us-central1-a"

  boot_disk {
    initialize_params {
      image = data.google_compute_image.debian.self_link
    }
  }

  network_interface {
    network = "default"
  }
}
```

`data.google_compute_image.debian.self_link` อ่านเหมือน resource address เป๊ะ ๆ แค่มี `data.` นำหน้า — label type กับ name ทำงานแบบเดียวกัน แต่ไม่มีอะไรจาก `data` block ที่จะโผล่เป็น create, update หรือ destroy ใน plan เลย เพราะมีหน้าที่อ่านอย่างเดียว

## Dependency graph

Terraform ไม่ได้ apply configuration ของคุณเรียงจากบนลงล่างตามที่เขียนไว้ แต่สร้าง **DAG** (directed acyclic graph) ของทุก resource และ data source แล้วใช้กราฟนั้นหาลำดับที่ถูกต้อง — พร้อมทั้งดูว่า resource ตัวไหนเป็นอิสระจากกันพอที่จะสร้าง **พร้อมกัน** ได้

edge ในกราฟนั้นมาจากสองที่

- **Implicit dependency** เมื่อไหร่ที่ argument ของ resource หนึ่งอ้างอิง attribute ของอีก resource หนึ่ง (เช่น `google_compute_subnetwork.app` อ้างอิง `google_compute_network.vpc.id` หรือ instance อ้างอิง ID ของ subnetwork) Terraform จะสรุปเองว่า resource ที่ถูกอ้างอิงต้องมีอยู่ก่อน
- **Explicit dependency** คือ `depends_on` บน resource ใช้ตอนที่ resource หนึ่งขึ้นกับอีกตัวจริง ๆ แต่ความสัมพันธ์นั้นไม่โผล่ผ่าน attribute reference ไหนเลย (เช่น IAM binding ที่ต้องมีอยู่ก่อนแอปเริ่มพึ่งพา โดยไม่มี argument เชื่อมกันตรง ๆ)

```hcl
resource "google_compute_network" "vpc" {
  name                    = "app-network"
  auto_create_subnetworks = false
}

resource "google_compute_subnetwork" "app" {
  name          = "app-subnet"
  ip_cidr_range = "10.0.1.0/24"
  region        = "us-central1"
  network       = google_compute_network.vpc.id # implicit dependency on google_compute_network.vpc
}

resource "google_compute_instance" "web" {
  name         = "web-vm"
  machine_type = "e2-medium"
  zone         = "us-central1-a"

  boot_disk {
    initialize_params {
      image = data.google_compute_image.debian.self_link
    }
  }

  network_interface {
    subnetwork = google_compute_subnetwork.app.id # implicit dependency on google_compute_subnetwork.app
  }
}
```

## `lifecycle` block: เปลี่ยนพฤติกรรม default ของ Terraform

ทุก resource รับ `lifecycle` block เป็นตัวเลือกได้ ซึ่งเปลี่ยนวิธีที่ Terraform plan การเปลี่ยนแปลงสำหรับ *resource นั้นตัวเดียว* โดยไม่เกี่ยวกับส่วนอื่นใน configuration argument สี่ตัวครอบคลุมความต้องการจริงแทบทั้งหมด

**`prevent_destroy`** เปลี่ยนการ destroy ที่ plan ไว้ให้กลายเป็น error หนัก ๆ แทนที่จะปล่อยให้ดำเนินต่อ — ราวกั้นความปลอดภัยสำหรับ resource ที่ต้องไม่ถูกลบโดยไม่ตั้งใจเด็ดขาด:

```hcl
resource "local_file" "protected" {
  filename = "${path.module}/protected.txt"
  content  = var.content

  lifecycle {
    prevent_destroy = true
  }
}
```

Error จริงจาก `terraform plan -destroy` กับบล็อกเดียวกันเป๊ะข้างบน:

```text
$ terraform plan -destroy
Plan: 0 to add, 0 to change, 1 to destroy.
╷
│ Error: Instance cannot be destroyed
│
│   on main.tf line 10:
│   10: resource "local_file" "protected" {
│
│ Resource local_file.protected has lifecycle.prevent_destroy set, but the
│ plan calls for this resource to be destroyed. To avoid this error and
│ continue with the plan, either disable lifecycle.prevent_destroy or reduce
│ the scope of the plan using the -target option.
╵
```

สังเกตว่า Terraform ยังคำนวณ plan อยู่ (`Plan: 0 to add, 0 to change, 1 to destroy` พิมพ์ก่อน) — `prevent_destroy` ถูกเช็คและหยุดการทำงานหลังจาก plan ตัดสินใจแล้วว่าต้อง destroy เท่านั้น ไม่ใช่ก่อนหน้านั้น

**`create_before_destroy`** สลับลำดับ replace default ปกติแล้วการ replace resource คือ destroy-แล้ว-create (`-/+` ใน plan); เมื่อตั้งค่านี้ Terraform จะสร้างตัวแทนก่อน แล้วค่อย destroy ตัวเก่าหลังจากตัวใหม่มีอยู่แล้ว — จำเป็นมากสำหรับอะไรก็ตามที่ช่วงเวลา "ไม่มีทั้งคู่" ยอมรับไม่ได้ อย่าง `google_compute_instance` ที่อยู่หลัง load balancer

```hcl
resource "local_file" "app" {
  filename = "${path.module}/app-${var.content}.txt"
  content  = var.content

  lifecycle {
    create_before_destroy = true
  }
}
```

Plan จริงหลังเปลี่ยน `var.content` (ซึ่งบังคับให้ `filename` เปลี่ยนตามไปด้วย และ `filename` บังคับให้ replace):

```text
$ terraform plan
  # local_file.app must be replaced
+/- resource "local_file" "app" {
      ~ content  = "v1" -> "v2" # forces replacement
      ~ filename = "./app-v1.txt" -> "./app-v2.txt" # forces replacement
        # (2 unchanged attributes hidden)
    }
Plan: 1 to add, 0 to change, 1 to destroy.
```

สัญลักษณ์คือตัวบ่งชี้: `+/-` (create แล้ว destroy) แทน `-/+` default (destroy แล้ว create) ที่เห็นทั่วทั้งคอร์สนี้ `create_before_destroy` เปลี่ยนแค่สัญลักษณ์ลำดับนั้น ไม่เปลี่ยนจำนวนบรรทัดของ plan เลย

**`ignore_changes`** บอก Terraform ให้เลิกมองการเปลี่ยนแปลงของ argument เฉพาะเป็น drift — มีประโยชน์เมื่อบางอย่างนอก Terraform (autoscaler, คนแก้ label ใน Cloud Console) คาดว่าจะเปลี่ยนค่า และการยืนยันค่าเดิมซ้ำทุก `apply` จะไปขัดกับมัน

```hcl
resource "terraform_data" "app" {
  input = {
    labels = { managed_by = "terraform" }
  }
  lifecycle {
    ignore_changes = [input]
  }
}
```

Plan จริงหลังเปลี่ยน `input` ใน configuration เอง:

```text
$ terraform plan
No changes. Your infrastructure matches the configuration.
```

ถ้าไม่มี `ignore_changes = [input]` การแก้คอนฟิกแบบเดียวกันนั้นจะ plan update จริง แต่มีมันแล้ว Terraform ไม่เทียบ `input` ปัจจุบันกับค่าคอนฟิกใหม่สำหรับ argument นั้นเลยด้วยซ้ำ — การเปลี่ยนแปลงมองไม่เห็นสำหรับ `plan` ไม่ใช่แค่ปล่อยให้เกิดครั้งเดียวแล้วค่อย track ใหม่

**`replace_triggered_by`** (อธิบายลึกพร้อมพิสูจน์จริงในบท Count and For Each) บังคับให้ resource ถูก replace ทุกครั้งที่ค่าที่*อ้างอิง*เปลี่ยน แม้ argument ของ resource เองจะไม่เปลี่ยนเลย — ปัญหาตรงข้ามกับ `ignore_changes`: แทนที่จะซ่อนการเปลี่ยนแปลง มันสร้างการ replace ขึ้นมาจากการเปลี่ยนแปลงที่ปกติมองไม่เห็นสำหรับ resource นี้

## `terraform graph` output จริง

`terraform graph` พิมพ์ dependency graph จริงที่ Terraform คำนวณ — ไม่ใช่คำอธิบาย แต่เป็น DOT output จริงที่ GraphViz (หรือเครื่องมืออ่าน DOT ไหนก็ได้) render ได้ตรง ๆ รันโดยไม่มี `-type` จะได้ resource-level summary graph เป็น default ซึ่งอ่านด้วยตาเปล่าง่ายที่สุด และไม่ต้องมี GCP credentials เลย — มันไม่เรียก Google Cloud API เลย เพียงแค่ resolve reference ที่มีอยู่แล้วในคอนฟิก:

```text
$ terraform graph
digraph G {
  rankdir = "RL";
  node [shape = rect, fontname = "sans-serif"];
  "data.google_compute_image.debian" [label="data.google_compute_image.debian"];
  "google_compute_instance.web" [label="google_compute_instance.web"];
  "google_compute_network.vpc" [label="google_compute_network.vpc"];
  "google_compute_subnetwork.app" [label="google_compute_subnetwork.app"];
  "google_storage_bucket.logs" [label="google_storage_bucket.logs"];
  "google_compute_instance.web" -> "data.google_compute_image.debian";
  "google_compute_instance.web" -> "google_compute_subnetwork.app";
  "google_compute_subnetwork.app" -> "google_compute_network.vpc";
}
```

นั่นคือกราฟจริงของ chain `google_compute_network.vpc` → `google_compute_subnetwork.app` → `google_compute_instance.web` ที่แสดงไว้ก่อนหน้าในบทนี้ บวกกับ `google_storage_bucket.logs` ที่ไม่เกี่ยวข้องกัน — อ่านตาม `rankdir = "RL"` (ขวาไปซ้าย) edge `A -> B` หมายถึง "A ขึ้นกับ B" ตรงกับเหตุผลเรื่อง implicit dependency จากหัวข้อก่อนหน้าเป๊ะ: `google_compute_instance.web` ขึ้นกับทั้ง `data.google_compute_image.debian` และ `google_compute_subnetwork.app` และ `google_compute_subnetwork.app` ขึ้นกับ `google_compute_network.vpc` `google_storage_bucket.logs` ไม่มี edge เข้าหรือออกจากอะไรเลย ซึ่งเป็นเหตุผลที่ Terraform สร้างมันพร้อมกับ chain ของ network ได้อย่างอิสระ

## Provider protocol: เกิดอะไรขึ้นจริง ๆ ตอน `terraform init`

ทุก provider — รวมถึง `hashicorp/google` — เป็น binary แยกต่างหากที่มี version เป็นของตัวเอง ที่ Terraform Core ดาวน์โหลดแล้วรันเป็น subprocess คุยกันผ่าน gRPC ด้วย protocol ตายตัว (protocol version 5 หรือ 6 แล้วแต่ SDK ของ provider) นี่คือเหตุผลที่ `terraform init` ต้องดาวน์โหลด binary เฉพาะต่อ OS/architecture แทนที่ Terraform จะ "รู้" วิธีคุยกับ GCP, AWS หรือ Azure เองมาตั้งแต่ต้น — provider plugin protocol, plugin handshake และเหตุผลที่ provider crash แล้วเกิด log แบบเฉพาะเจาะจง จะอธิบายลึกพร้อม trace จริงของ `TF_LOG=TRACE` ตอน provider เริ่มทำงาน ใน [Provider Plugin Protocol](/terraform-gcp/en/terraform-internals/provider-plugin-protocol/) ในโมดูล Terraform Internals

## Mental Model

ทุกอย่างในบทนี้มีหน้าที่เดียว: ช่วยให้ Terraform สร้าง plan ที่ถูกต้องก่อนที่มันจะแตะ GCP เลย `resource`/`data` block และการอ้างอิงของมันสร้าง dependency graph; การ override ด้วย `lifecycle` คือข้อยกเว้นที่ซ้อนอยู่*บน*พฤติกรรมปกติของกราฟนั้นสำหรับ resource ทีละตัว (หยุดหนัก ๆ, สลับลำดับ, จุดบอดที่ตั้งใจ, edge เพิ่ม) — ไม่มีตัวไหนเปลี่ยนหน้าตาของกราฟเลย เปลี่ยนแค่สิ่งที่ Terraform ทำเมื่อไปถึง node นั้น ตัว provider เองเป็น process แยกที่ Terraform Core คุยด้วยผ่าน protocol ตายตัว ซึ่งเป็นเหตุผลที่ "provider" กับ "Terraform" มี version อิสระจากกันได้ — `required_providers` pin ตัวหนึ่ง `required_version` pin อีกตัว

## Trade-offs

| ตัวเลือก | ข้อดี | ต้นทุน |
|---|---|---|
| `prevent_destroy` | หยุดหนัก ๆ ป้องกัน destroy โดยไม่ตั้งใจ พิสูจน์ข้างบนด้วย error จริงก่อน API call ใด ๆ | บล็อก*ทุก*การ destroy รวมถึงที่ตั้งใจด้วย — ต้องลบออกจากโค้ด (ไม่ใช่แค่ `-target` เลี่ยง) เพื่อรื้อ resource จริง ๆ |
| `create_before_destroy` | ไม่มีช่วง "ไม่มีทั้งคู่" ตอน replace พิสูจน์ข้างบนผ่านสัญลักษณ์ลำดับ `+/-` | ต้องมีสองชุดอยู่ร่วมกันชั่วขณะ — ปัญหาสำหรับอะไรที่มี uniqueness constraint (ชื่อตายตัว, static IP ที่จองไว้) นอกจาก argument นั้นจะเปลี่ยนด้วย |
| `ignore_changes` | หยุด Terraform สู้กับการเปลี่ยนแปลงนอกระบบ พิสูจน์ข้างบนด้วย "No changes" จริงแม้แก้คอนฟิก | ค่าจริงของ argument ที่ถูก ignore ใน console/API เบี่ยงห่างจากที่อยู่ใน `.tf` ได้ไม่จำกัด โดย `plan` ไม่พูดถึงเลย |
| `replace_triggered_by` | ทำให้ dependency ที่ปกติมองไม่เห็นบังคับ replace จริงได้ อย่างตั้งใจ | ต้นทุนเดียวกับ forced replacement ใด ๆ: destroy + recreate ทั้งหมด ไม่ใช่ update บางส่วน |
| `terraform graph` (default ไม่มี `-type`) | สะอาด เป็น summary ระดับ resource — ตัวที่ควรอ่านด้วยตาเปล่า พิสูจน์ข้างบน และไม่ต้องมี GCP credentials | ไม่มี provider node, internal `(expand)` และ action เฉพาะ plan ที่ `-type=plan` แสดง — ไม่ใช่ภาพเต็มที่ Terraform เดินจริง |

## ความเข้าใจผิดที่พบบ่อย

- **"`prevent_destroy` หยุด Terraform ไม่ให้คำนวณ destroy plan เลยด้วยซ้ำ"** พิสูจน์ข้างบนแล้วว่าไม่ใช่: บรรทัดสรุป plan (`Plan: 0 to add, 0 to change, 1 to destroy`) พิมพ์ *ก่อน* error — `prevent_destroy` ดักการทำงานหลังจาก plan เสร็จ ไม่ใช่ก่อน
- **"`create_before_destroy` หลีกเลี่ยงการเปลี่ยนจำนวนบรรทัดของ plan diff"** มันเปลี่ยนแค่*สัญลักษณ์* (`+/-` กับ `-/+`) พิสูจน์ข้างบน ไม่เปลี่ยนจำนวนบรรทัด — `1 to add, 0 to change, 1 to destroy` เหมือนกันทั้งคู่
- **"`ignore_changes` แค่ ignore drift ครั้งแรก แล้วก็ resync"** พิสูจน์ข้างบนแล้วว่าไม่ใช่การข้ามครั้งเดียว — ทุก `plan` ถัดไปยังมองว่า argument นั้นมองไม่เห็นต่อไปเรื่อย ๆ จนกว่า `lifecycle` block เองจะถูกแก้
- **"Terraform apply resource ตามลำดับที่เขียนในไฟล์"** พิสูจน์ข้างบนด้วย `terraform graph` จริง: ลำดับมาจาก dependency graph ทั้งหมด ไม่ใช่ตำแหน่งในไฟล์ — `google_storage_bucket.logs` ที่เขียนไว้ท้ายสุด ไม่มี edge เลยและ apply ก่อนได้
- **"provider เป็นส่วนหนึ่งของ Terraform binary compile ติดมาด้วย"** มันเป็น binary ที่ดาวน์โหลดแยกต่างหาก รันเป็น subprocess ผ่าน gRPC — อธิบายพร้อม trace จริงในโมดูล Terraform Internals นี่คือเหตุผลที่ `terraform init` ต้องใช้ network access สำหรับ provider ที่ Terraform เองไม่ได้มากับตัว

## อ่านโค้ดที่ AI สร้างให้

- `lifecycle { prevent_destroy = true }` ที่ใส่ในทุก resource "เพื่อความปลอดภัย" รวมถึงตัวที่จำเป็นต้องถูก destroy จริงเป็นส่วนหนึ่งของการทำงานปกติ (resource ชั่วคราว, อะไรก็ตามที่อยู่หลัง `count`/`for_each` ที่หดตัวจริง ๆ) — พิสูจน์ข้างบนแล้วว่านี่เปลี่ยน destroy ที่ตั้งใจให้เป็น error หนัก ๆ ที่ต้องแก้ด้วยการแก้โค้ด ไม่ใช่คำเตือนเบา ๆ
- `create_before_destroy = true` ที่ใส่ใน resource ที่มี uniqueness constraint บน argument ที่ไม่ได้เปลี่ยน (`name` ตายตัว, static IP ที่จองไว้) — ตัวแทนจะสร้างไม่สำเร็จเพราะตัวเก่าที่ยังไม่ถูก destroy ยังถือชื่อนั้นอยู่
- `ignore_changes = [labels]` (หรือแย่กว่านั้น `ignore_changes = all`) ที่ copy มาจากตัวอย่างโดยไม่เช็คว่า label ของ resource *นี้* ควรถูกจัดการโดย Terraform ไหม — พิสูจน์ข้างบนแล้วว่านี่ซ่อน drift แบบเงียบและตลอดไป ไม่ใช่แค่ครั้งเดียว
- `depends_on` ที่หายไปเมื่อ comment อ้างว่า "X ต้องมีก่อน Y" แต่ไม่มี argument reference ไหนเข้ารหัสสิ่งนั้นจริง — พิสูจน์ข้างบนแล้วว่า implicit dependency ต้องการ attribute reference จริง comment เฉย ๆ ไม่เข้ากราฟเลย
- `google_compute_instance` ที่ generate มาโดยไม่มี `network_interface` block เลย — นี่ไม่ใช่ตัวเลือก `terraform validate` จะปฏิเสธทันทีเพราะ `network_interface` เป็น block ที่จำเป็น
- โค้ดที่อ้างพฤติกรรมของ provider version เฉพาะโดยไม่เช็ค `required_providers` — หัวข้อ provider protocol ข้างบนเตือนว่า "Terraform" กับ "Google provider" เป็นซอฟต์แวร์สอง version อิสระที่คุยกันผ่าน wire protocol ตายตัว

<Callout title="สรุปหนึ่งบรรทัด">
configuration แบบ HCL ประกอบด้วย **block**: `terraform` ประกาศ provider และ version ที่ต้องใช้, `provider` ตั้งค่าว่า Terraform คุยกับ GCP ยังไง, `resource` block (ระบุด้วย **type** และ **name** ที่คุณเลือก รวมกันเป็น **address**) ประกาศสิ่งที่ Terraform ควรสร้างและจัดการ ส่วน `data` block มีหน้าที่ **อ่าน** infrastructure ที่มีอยู่แล้วเท่านั้นโดยไม่เข้าไปเป็นเจ้าของ Terraform สร้าง **dependency graph (DAG)** จาก implicit reference กับ `depends_on` แบบ explicit แล้ว apply resource ที่เป็นอิสระต่อกันพร้อมกัน — พิสูจน์ข้างบนด้วย `terraform graph` DOT dump จริง **`lifecycle`** block override พฤติกรรม default ของ Terraform ต่อ resource: **`prevent_destroy`** เปลี่ยน destroy ที่ plan ไว้ให้เป็น error หนัก ๆ (พิสูจน์ข้างบน), **`create_before_destroy`** สลับลำดับ replace เป็น `+/-` แทน `-/+` (พิสูจน์ข้างบน), **`ignore_changes`** ทำให้การเปลี่ยน argument เฉพาะมองไม่เห็นต่อ `plan` (พิสูจน์ข้างบนด้วย "No changes" จริง) และ **`replace_triggered_by`** บังคับ replace จากสัญญาณภายนอก ทุก provider เป็น binary แยกที่คุยผ่าน gRPC protocol ตายตัวกับ Terraform Core อธิบายในโมดูล Terraform Internals
</Callout>
