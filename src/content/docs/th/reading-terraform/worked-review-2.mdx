## Feature ที่ต้องทำ

Prompt คือ: *"ตั้ง Terragrunt live tree ที่มี dev กับ prod environment แต่ละอันมี network unit และ app unit ที่ depend บนมัน"* สิ่งที่ตามมาคือ draft แรกแบบที่ AI assistant ส่งกลับมาให้กับ prompt แบบนี้พอดี — `root.hcl` ที่ใช้ร่วมกัน, `terragrunt.hcl` สี่ไฟล์ที่ดูสมเหตุสมผลรายตัว, และ CI snippet ที่อ่านแล้วเหมือน Terragrunt tutorial ทุกอันที่ตีพิมพ์ก่อน CLI redesign 1.1 มี **bug จริง 8 ข้อ**; ดู **[AI bug catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)** สำหรับ pattern ทั่วไปเบื้องหลังแต่ละข้อ เจ็ดในแปดข้อนี้เป็น mechanics ของ Terragrunt-core ที่ไม่ขึ้นกับ provider เหมือนกันเป๊ะกับ worked review 2 ของ review ทั้งสองฝั่งก่อนหน้า — พิสูจน์สดใหม่ที่นี่ ใน repo นี้ กับ `google` — บวกอีกหนึ่ง bug ที่เฉพาะ backend GCS จริงๆ แทนคู่ `dynamodb_table`/`use_lockfile` ของ AWS และ `use_azuread_auth` ที่หายไปของ azurerm ทุกข้อที่กล่าวถึงด้านล่างพิสูจน์ด้วย `terragrunt hcl validate`/`render`/`run --all`/`find --dag` จริง กับ Terragrunt 1.1.0 และ Terraform 1.16.4 โดยใช้ `backend = "local"` แทน backend GCS จริง — ตามธรรมเนียมของคอร์สนี้ การพิสูจน์ offline ไม่แตะ GCP จริงเลย

### `network` unit: `dev` กับ `prod` มี `locals` เหมือนกันเป๊ะ

**อาการ — จริง บนไฟล์ที่ AI สร้างจริง:**

```text
$ diff live/dev/network/terragrunt.hcl live/prod/network/terragrunt.hcl
(no output -- the files are byte-identical)
```

ทั้งสองไฟล์ประกาศ `environment = "dev"`, `project = "acme-dev-123456"` — รวมถึงข้างใน `live/prod/network/terragrunt.hcl` ด้วย

<SpotTheBug code={`# live/prod/network/terragrunt.hcl
locals {
  environment = "dev"
  project     = "acme-dev-123456"
}`}>
bug เดียวกับ **[AI bug catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)** entry 17 — `terragrunt hcl validate`/`hcl format --check` ผ่านทั้งคู่ ไม่มีอะไรเป็น HCL ที่ invalid เลย และด้วย `backend = "local"` สำหรับการพิสูจน์ offline ของคอร์สนี้ ไม่มีอะไรพังตอน `plan` ด้วย เทียบกับ backend GCS จริงที่เล็งไป `project = "acme-dev-123456"` จากทั้ง `dev` และ `prod` นี่คือการ deploy `prod` เข้า GCP project ของ `dev` แบบเงียบๆ วิธีแก้: ย้ายค่าที่ต้องต่างกันต่อ environment ไปไว้ `env.hcl` ต่อ environment แล้วให้ `network/terragrunt.hcl` แต่ละตัวกลายเป็นเหมือนกันกับ sibling ของมัน อ่าน `include.env.locals.*` แทน
</SpotTheBug>

### `include` ตัวที่สองสำหรับค่าที่ share กัน ประกาศโดยไม่มี `expose = true`

```hcl

  project = include.env.locals.project

**อาการ — `terragrunt render` จริง:**

$ terragrunt render --format json
Error: Unsupported attribute

  on unit/terragrunt.hcl line 15:
  15:   project = include.env.locals.project

This object does not have an attribute named "env".
```

<SpotTheBug code={`include "env" {
  path           = find_in_parent_folders("env.hcl")

mechanism เดียวกับ **[Dry Configuration with Include](/terraform-gcp/th/terragrunt-fundamentals/dry-configuration-with-include/)** — `expose = true` คือสิ่งที่ทำให้เนื้อหาที่ parse แล้วของ include อ่านได้ผ่าน `include.NAME.*` วิธีแก้: เพิ่ม `expose = true` เข้า include block ของ `env`

### `root.hcl`: GCS `remote_state` ไม่มี `prefix` — สอง unit share state object เดียวกันแบบเงียบๆ

```hcl
# root.hcl (excerpt)
remote_state {
  backend = "gcs"
  config = {
    bucket   = "acme-terraform-state"
    project  = "acme-prod-123456"
    location = "US"
  }
}
```

**อาการ — จริง `terragrunt run -- init -backend=false` กับ `root.hcl` นี้เป๊ะ รันจากสอง unit ต่างกัน `network` กับ `app` (ธรรมเนียมของคอร์สนี้ในการพิสูจน์ผลของ `generate` — ไม่ต้องมี GCS bucket จริง แค่เนื้อหา `backend.tf` ที่ generate ออกมาจริงก็พอ):**

```text
$ cd network && terragrunt run --non-interactive --no-color -- init -backend=false && cat backend.tf
# Generated by Terragrunt. Sig: nIlQXj57tbuaRZEa
terraform {
  backend "gcs" {
    bucket = "acme-terraform-state"
  }
}

$ cd ../app && terragrunt run --non-interactive --no-color -- init -backend=false && cat backend.tf
# Generated by Terragrunt. Sig: nIlQXj57tbuaRZEa
terraform {
  backend "gcs" {
    bucket = "acme-terraform-state"
  }
}
```

<SpotTheBug code={`remote_state {
  backend = "gcs"
  config = {
    bucket   = "acme-terraform-state"
    project  = "acme-prod-123456"
    location = "US"
  }
}`}>
`backend.tf` ที่ generate ออกมาทั้งสองไฟล์ **เหมือนกันเป๊ะ byte-ต่อ-byte** พิสูจน์แล้วด้านบนด้วยการรัน `init -backend=false` จริงแยกกันสองครั้ง — `bucket = "acme-terraform-state"` แล้วไม่มีอะไรอื่นเลย `project`/`location` ควบคุมการ auto-create bucket ไม่ใช่การ address state ของ backend block เอง และไม่เคยมี `prefix` ตั้งไว้เลยเพื่อให้แต่ละ unit มี path ของตัวเองแบบที่ `path_relative_to_include()` ทำให้ `key` (AWS) หรือ `key` (azurerm) ถ้าไม่มีมัน `network` กับ `app` จะเล็งไป state object เดียวกันเป๊ะที่ bucket root แบบเงียบๆ — unit ตัวที่สองที่รัน `apply` จะอ่านและเขียนทับ state ของ unit ตัวแรก วิธีแก้: เพิ่ม `prefix = "${path_relative_to_include()}/terraform.tfstate"` เข้า `remote_state.config` เหมือน `key` ของ review ทั้งสองฝั่งก่อนหน้า
</SpotTheBug>

## โค้ดที่แก้แล้ว

```hcl
# root.hcl
remote_state {
  backend  = "local"
  generate = { path = "backend.tf", if_exists = "overwrite_terragrunt" }
  config   = { path = "${get_terragrunt_dir()}/terraform.tfstate" }
}
```

<Callout title="ทำไม proof tree นี้ใช้ backend = local">
ตามธรรมเนียมของคอร์สนี้ `remote_state` แบบ GCS จริงต้องมี bucket จริงที่คอร์สนี้ไม่ provision เลย ทุกคำกล่าวอ้างในบทนี้ที่อิง mechanics ของ `remote_state` มากกว่ารายละเอียด backend เอง — `include`, `dependency`, `find_in_parent_folders`, layout ของ live tree เอง — เหมือนกันทั้งคู่ ต่างกันแค่ `backend = "gcs"` เทียบกับ `"local"` และ `config` ที่ตามมา deploy จริงของ tree นี้ใช้ block `gcs` ของ "โค้ดที่ AI สร้าง" พร้อมเพิ่ม `prefix = "${path_relative_to_include()}/terraform.tfstate"` (วิธีแก้ด้านบน) ไม่ใช่อันนี้
</Callout>

| # | Bug | วิธีแก้ |
|---|---|---|
| 1 | `run-all`/`plan-all` ใน CI script | `run --all` — real "unknown command" rejection ทั้งคู่ ก่อนแก้ |
| 2 | `--terragrunt-non-interactive` และ flag prefix ก่อน 1.1 อื่นๆ | `--non-interactive` เปล่าๆ ฯลฯ — real "not a Terragrunt flag" rejection ก่อนแก้ |

## Mental Model

สี่ใน bug แปดข้อนี้ (1, 2, 3, 6) เป็น hard failure ที่ชัดทันทีระดับ CLI/HCL-evaluation เหมือนกับ review ทั้งสองฝั่งก่อนหน้า ข้อหนึ่ง (4) เป็น hard failure แต่เกิดเฉพาะ `run --all plan` ครั้งแรกกับ environment สดใหม่จริงๆ เท่านั้น ข้อหนึ่ง (7) เป็น hard failure เฉพาะ state ที่ไม่เคยถูก apply ที่ระดับ Terraform สองข้อที่เหลือ (5, 8) ไม่ error เลย — และ entry 8 คือ bug ข้อเดียวในบทนี้ทั้งหมดที่เฉพาะ GCS จริงๆ: แทนที่จะเป็น argument `dynamodb_table` ที่ deprecated (AWS) หรือ backend ที่ default ไป shared key แบบเงียบๆ (azurerm) ช่องว่างเทียบเท่าที่นี่คือ unit สองตัวที่มีโครงสร้างต่างกันจริง generate backend configuration เหมือนกันเป๊ะ — ความเสี่ยง state ชนกันจริง ที่ `hcl validate` ไม่มีทางสังเกตได้เลย เพราะไฟล์ที่ generate ทั้งสองไฟล์ valid สมบูรณ์รายตัว

## ความเข้าใจผิดที่พบบ่อย

- **"ถ้า `terragrunt hcl validate` ผ่าน แปลว่า multi-environment tree ปลอดภัยที่จะ deploy จริง"** พิสูจน์แล้วด้านบน: `hcl validate` กับ `network` unit ที่เหมือนกันเป๊ะสองตัวคืนค่า error ศูนย์ข้อ — HCL validation ไม่มีแนวคิดเรื่อง "ค่านี้ควรต่างจากไฟล์ sibling นั้น" เลย และเช่นเดียวกันกับ unit สองตัวที่ generate `backend.tf` เหมือนกันเป๊ะ
- **"`dependency` block ที่ไม่มี `mock_outputs` พังแค่ `apply` เท่านั้น ไม่เคยพัง `plan`"** พิสูจน์แล้วด้านบน: บน environment สดใหม่สมบูรณ์ที่ dependency ไม่เคยถูก apply เลยแม้แต่ครั้งเดียว `run --all plan` เองก็พัง
- **"`project`/`location` ใน `remote_state.config` แบบ GCS scope state ต่อ unit เหมือน `key`/`prefix` ที่อื่น"** พิสูจน์แล้วด้านบน: unit สองตัวที่มีโครงสร้างต่างกันจริง (`network`, `app`) generate `backend.tf` เหมือนกันเป๊ะ ต่างกันแค่ไม่มีอะไรเลย — `project`/`location` ควบคุมการ auto-create bucket ไม่เคย address state เลย มีแค่ `prefix` เท่านั้นที่ทำแบบนั้น และไม่เคยถูกตั้งเลย
