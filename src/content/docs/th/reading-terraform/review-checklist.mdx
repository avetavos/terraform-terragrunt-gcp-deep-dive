## Versions & providers

- ทุก `required_providers` constraint เป็น `~>` ไม่ใช่ `>=` ใช่ไหม? Constraint ที่ลอยตัว resolve ไปที่ release ใหม่สุดของ registry ในวันที่ `init` รัน ดู **[AI Bug Catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)**, entry 1
- `.terraform.lock.hcl` commit ไว้แล้วหรือยัง — ไม่ได้ gitignore พร้อมกับ `.terraform/`? ดู entry 4
- `terraform validate -json` กลับมาโดยไม่มี **warning** เลยใช่ไหม ไม่ใช่แค่ไม่มี error? Argument ที่ deprecated (`acl`, `managed_policy_arns`) ยัง validate และ plan ผ่านสำเร็จ ดู entry 2
- มี module ไหนประกาศ `provider` block ของตัวเองหรือไม่? มัน validate ผ่านด้วยตัวเองสบายๆ และพังก็ต่อเมื่อผู้เรียกใช้ต้องการ `count`/`for_each`/`depends_on` ดู entry 3

## State & backend

- กลไกล็อกของ backend ตรงกับสิ่งที่ Terraform/backend version นี้รองรับจริงหรือไม่ — `use_lockfile` (S3, stable ตั้งแต่ 1.11) แทนที่ `dynamodb_table` ที่ deprecated แล้ว? ดู **[AI Bug Catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)**, entry 5 และ **[The State File](/terraform-gcp/th/state-management/the-state-file/)**
- `terraform_remote_state` data source ทุกตัวชี้ไปที่ `key`/`path` ที่ apply ไปแล้วจริงหรือไม่? ไม่มี mock fallback เลย — state ที่หายไปพัง plan ทั้งหมดหนักๆ ดู entry 6

## Variables

- default ของ `nullable = false` variable เคยแทนที่ `null` ที่ผู้เรียกส่งมาตรงๆ อย่างเงียบๆ หรือไม่ โดยไม่มีอะไรใน `plan`/`apply` output บอกเรื่องการแทนที่เลย? ดู **[AI Bug Catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)**, entry 7
- variable ไหนที่เป็น `ephemeral` มี default เป็น secret ตรงๆ หรือไม่? มันยังรั่วเข้าไปใน `show -json` ของ plan ที่ save ไว้ แม้จะไม่เข้า state เลยก็ตาม ดู entry 8

## Resources & lifecycle

- ใช้ `count` กับ list ไหนที่อาจถูกจัดลำดับใหม่ได้ ในที่ที่ `for_each` เป็นทางเลือกปลอดภัยทางเดียวหรือไม่? การเอา element ตรงกลางออกเลื่อน index ทุกตัวที่ตามมา ดู **[AI Bug Catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)**, entry 10
- `lifecycle { prevent_destroy = true }` อยู่บน resource ที่สำคัญจริงหรือไม่ — ตรวจตรงๆ ไม่ใช่สมมติจาก resource ใกล้ๆ? ดู entry 9 พิสูจน์ด้วย `plan -destroy` จริงที่ destroy database ที่ไม่ถูกป้องกันได้โดยไม่มีอะไรต้านเลย
- `for_each` ไหน derive key มาจาก computed attribute ของ resource ที่ managed อีกตัวหรือไม่? Error "Invalid for_each argument" จริงและปัจจุบัน — ดู entry 11
- ใช้ `null_resource` ในที่ที่ `terraform_data` (1.4+) ตัดทั้ง provider dependency เพิ่มออกไปสำหรับพฤติกรรมที่เท่ากันหรือไม่? ดู entry 12
- มี argument ไหนที่ดู copy มาจาก resource type ที่คล้ายกันแต่ไม่ใช่ตัวเดียวกันหรือไม่ (`force_destroy` บน `google_compute_instance`, จริงบน `google_storage_bucket` แต่ไม่ใช่ที่นี่)? Error "Unsupported argument" จริง — ดู entry 13

## Modules

- ทุก `source` ที่ไม่ใช่ registry pin revision ไว้แล้วหรือยัง — `?ref=<tag-or-sha>` สำหรับ source แบบ `git::`, `version` ตรงๆ สำหรับ registry module? ถ้าไม่มี Terraform จะ track default branch ของ `HEAD` อย่างเงียบๆ ดู **[AI Bug Catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)**, entry 14
- `depends_on` บน module call ไหนมีไว้เพื่อ "แก้" ข้อร้องเรียนเรื่องลำดับที่จริงๆ แล้วเป็น reference cycle จริงหรือไม่? ไม่มี `depends_on` ใดกด `Error: Cycle` จริงไว้ได้ ดู entry 15

## Terragrunt live tree

- มีอะไรอ้างอิง `run-all`/`plan-all` หรือไม่? ทั้งคู่เป็นคำสั่งที่ไม่รู้จักตั้งแต่ Terragrunt 1.1 CLI redesign — ปฏิเสธจริงและทันที ดู **[AI Bug Catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)**, entry 16
- ไฟล์ `terragrunt.hcl` ของสอง environment เคยมีค่า `account_id`/`region`/subscription/project *เหมือนกันทุกตัวอักษร*ใน `inputs` หรือไม่? `terragrunt hcl validate` จับ copy-paste ที่ valid ทาง syntax แบบนี้ไม่ได้ ดู entry 17 พิสูจน์ด้วย diff ของ `dev`/`prod` ที่เหมือนกันทุกตัวอักษรจริง

## CI & policy

- `-auto-approve` เคยรันกับ plan ที่ *สดใหม่* แทนที่จะเป็นไฟล์ `plan -out` ที่ save และ review แล้วหรือไม่? ดู **[AI Bug Catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)**, entry 18 พิสูจน์ด้วย apply เทียบข้างกันจริง
- GitHub Action จาก third-party ทุกตัว pin ด้วย commit SHA เต็ม ไม่ใช่ tag ที่เปลี่ยนได้อย่าง `@master`/`@main` ใช่ไหม? ดู entry 19
- Policy Rego ไหนใช้ syntax ก่อน v1 (`deny[msg] { ... }`) หรือไม่? มัน load ไม่ผ่านเลยภายใต้ OPA/conftest ปัจจุบัน — ดู entry 20 พิสูจน์ด้วย `rego_parse_error` จริง
- ทุก rule ของ `.tflint.hcl` อ้างอิงสิ่งที่ ruleset `tflint-ruleset-google` เล็กๆ ที่เน้น IAM (รวม 6 rule) มีอยู่จริงหรือไม่ — ไม่ใช่สมมติว่ามี resource-shape check แบบที่ ruleset ของ cloud อื่นที่ใหญ่กว่ามี? ดู entry 21 พิสูจน์ด้วย error "Rule not found" จริงและทันทีที่นี่
- มี secret จริงถูก commit ในไฟล์ `.tfvars` หรือไม่ หรือเหลืออยู่ใน `terraform.tfstate` เป็น plaintext แม้ output จะติด `sensitive` แล้วหรือไม่? ดู entry 22–23

## Tooling

- `terraform validate -json | jq '.diagnostics[]'` ถูกเช็คหา **warning** ด้วยหรือไม่ ไม่ใช่แค่ exit code ที่ไม่ใช่ศูนย์? ดู **[Verification Tools](/terraform-gcp/th/reading-terraform/verification-tools/)**
- CI รัน `terraform plan -detailed-exitcode` จริงและตรวจ `show -json` ของ plan ที่ save ไว้ด้วย policy tool จริง (conftest, checkov) ไม่ใช่แค่กวาดตาดู plan text หรือไม่? ดู **[Verification Tools](/terraform-gcp/th/reading-terraform/verification-tools/)**
- `terragrunt hcl validate`/`render` รันใน CI ก่อน `run --all plan` เพื่อจับ syntax error ก่อนที่ tree 10 หน่วยจะ apply ไปครึ่งหนึ่งหรือไม่? ดู **[Verification Tools](/terraform-gcp/th/reading-terraform/verification-tools/)**
