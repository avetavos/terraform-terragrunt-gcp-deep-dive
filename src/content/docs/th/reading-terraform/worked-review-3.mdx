## Feature ที่ต้องทำ

Prompt คือ: *"เขียน GitHub Actions pipeline ที่รัน Terraform plan บน pull request และ apply บน merge เข้า main โดยใช้ Workload Identity Federation แทน GCP key ที่เก็บไว้ พร้อม policy check"* สิ่งที่ตามมาคือ draft แรกแบบที่ AI assistant ส่งกลับมาให้กับ prompt แบบนี้พอดี — YAML ที่ดูสมเหตุสมผล, action `google-github-actions/auth` จริง, Rego policy ที่อ่านแล้วเหมือน OPA tutorial ทุกอัน มี **bug จริง 10 ข้อ**; ดู **[AI bug catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)** สำหรับ pattern ทั่วไปเบื้องหลังหลายข้อ (entry 4, 18, 19, 20, 22) เก้าในสิบข้อนี้เป็น CI/policy mechanics เดียวกันเป๊ะที่ไม่ขึ้นกับ provider เหมือนกับ worked review 3 ของ review ทั้งสองฝั่งก่อนหน้า — พิสูจน์สดใหม่ที่นี่ ใน repo นี้ — บวกอีกหนึ่ง bug ที่เฉพาะ Workload Identity Federation ของ GCP จริงๆ บทนี้เสริม — และลิงก์ไปหา — **[CI/CD for Infrastructure](/terraform-gcp/th/production-and-ecosystem/ci-cd-for-infrastructure/)** ที่แสดง pipeline ที่แก้แล้วเต็มรูปแบบ ทุกข้อที่กล่าวถึงด้านล่างพิสูจน์ด้วย `actionlint`, `tflint`, `checkov`, และ `conftest` จริง (ผ่าน `docker run --rm` กับ image `rhysd/actionlint`, `ghcr.io/terraform-linters/tflint`, `bridgecrew/checkov`, และ `openpolicyagent/conftest` ที่ pin ไว้) บวก exit code จริงของ Terraform และ `terragrunt run --all plan --out-dir` จริง

## โค้ดที่ AI สร้าง

```yaml
# .github/workflows/terraform.yml, as generated -- fragment, not a collected fence
name: terraform
on:
  pull_request:
  push:
    branches: [main]

jobs:
  plan:
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/checkout@master
      - uses: hashicorp/setup-terraform@v3
      - name: Authenticate to GCP via Workload Identity Federation
        uses: google-github-actions/auth@v3
        with:
          workload_identity_provider: projects/111122223333/locations/global/workloadIdentityPools/github-pool/providers/github-provider
          service_account: github-actions-terraform@acme-prod-123456.iam.gserviceaccount.com
      - run: terraform init
      - name: plan
        run: |
          echo "TF_VAR_db_password=$TF_VAR_db_password"
          terraform plan -detailed-exitcode -out=$PLAN_FILE
        env:
          PLAN_FILE: tfplan
          TF_VAR_db_password: ${{ secrets.DB_PASSWORD }}

  apply:
    needs: plan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@master
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve
```

## เดินรีวิวทีละ bug

### Workflow: `actions/checkout@master` — branch ที่เปลี่ยนแปลงได้ ถูกใช้ราวกับ pin ไว้แล้ว

**อาการ — `actionlint` จริง, `rhysd/actionlint`, container แบบ one-shot:**

```text
$ docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -color
(no output -- 0 exit code)
```

<SpotTheBug code={`- uses: actions/checkout@master`}>
bug เดียวกับ **[AI bug catalog](/terraform-gcp/th/reading-terraform/ai-bug-catalog/)** entry 19 และ mechanics เดียวกับ entry 1 ของ review ทั้งสองฝั่งก่อนหน้า — พิสูจน์สดใหม่ที่นี่ `actionlint` ต้องการแค่มี token `@ref` อยู่จริงตาม syntax เท่านั้น การลบมันออกไปเลย (`uses: actions/checkout` ไม่มี `@` เลย) คือ error จริงที่มันจับได้ — ยืนยันแยกต่างหาก: `specifying action "actions/checkout" in invalid format because ref is missing` แต่ `@master` ให้ ref ที่ valid ตาม syntax `actionlint` เลยยอมรับเหมือนกับ commit SHA ที่ pin ไว้ วิธีแก้: `uses: actions/checkout@<40-char-sha>  # v5.0.0`
</SpotTheBug>

### Workflow: ปัญหา shellcheck ที่ `actionlint` จับได้จริง

**อาการ — `actionlint` จริง กับ `run: terraform plan -detailed-exitcode -out=$PLAN_FILE`:**

```text
$ docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -color
.github/workflows/terraform.yml:16:9: shellcheck reported issue in this script: SC2086:info:1:40: Double quote to prevent globbing and word splitting [shellcheck]
   |
16 |         run: |
   |         ^~~~
```

<SpotTheBug code={`run: |
  terraform plan -detailed-exitcode -out=$PLAN_FILE`}>
`actionlint` ฝัง `shellcheck` เข้าไปกับทุก multi-line `run:` script `$PLAN_FILE` ที่ไม่ quote เจอ word-splitting และ glob expansion จาก shell ได้ วิธีแก้: `-out="$PLAN_FILE"`
</SpotTheBug>

### Workflow: `env: TF_VAR_db_password` ถูก echo ในบรรทัด debug

**อาการ — จริง `env` ทำซ้ำสิ่งที่ environment ของ CI runner หน้าตาเป็นเมื่อ `env:` ตั้งตัวแปรที่มาจาก secret:**

```text
$ export TF_VAR_db_password="SuperSecret123"
$ env | grep TF_VAR_db_password
TF_VAR_db_password=SuperSecret123
```

<SpotTheBug code={`- name: plan
  run: |
    echo "TF_VAR_db_password=$TF_VAR_db_password"
    terraform plan -detailed-exitcode -out=$PLAN_FILE
  env:
    TF_VAR_db_password: \${{ secrets.DB_PASSWORD }}`}>
GitHub Actions มาสก์ *ค่า secret ที่รู้จักแล้ว* ใน raw log output ก็จริง แต่พิสูจน์แล้วด้านบน ข้อเท็จจริงทาง shell ที่แท้จริงคือ `TF_VAR_db_password` เป็น environment variable ธรรมดาสามัญทันทีที่ `env:` ตั้งมัน วิธีแก้: อย่า echo ตัวแปรที่มาจาก secret เลย แม้จะเพื่อ debug ก็ตาม
</SpotTheBug>

### `apply`: ไม่มี plan ที่บันทึกไว้ — `terraform apply -auto-approve` plan ใหม่ตั้งแต่ต้น

**อาการ — จริง เทียบกันตรงๆ ก่อนอื่น `apply` ที่ไม่มี plan file ที่บันทึกไว้:**

```text
$ terraform apply -auto-approve
terraform_data.x: Refreshing state...
Plan: 1 to add, 0 to change, 0 to destroy.
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
```

แล้ว plan ที่บันทึกจริงถูก apply ผ่าน path ของไฟล์แทน:

```text
$ terraform plan -out=tfplan
$ terraform apply tfplan
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
```

<SpotTheBug code={`- run: terraform init
- run: terraform apply -auto-approve`}>
job `apply` ไม่เคย download plan ที่ job `plan` คำนวณไว้เลย พิสูจน์แล้วด้านบน: `apply -auto-approve` ที่ไม่มี plan file พิมพ์ `Refreshing state...` / `Plan:` ของตัวเองสดใหม่ก่อน apply การ apply plan file จริงที่บันทึกไว้แทนไม่พิมพ์บรรทัดไหนเลย วิธีแก้: `terraform plan -out=tfplan` เป็น build artifact ใน job `plan` download แล้ว apply ตรงตัว (`terraform apply tfplan`) ใน job `apply`
</SpotTheBug>

### `plan`: คำนวณ `-detailed-exitcode` แต่ exit code สามแบบไม่เคยถูกอ่านจริง

**อาการ — จริง command เดียวกันเป๊ะ exit code จริงต่างกันในสองสถานะ:**

```text
$ terraform plan -detailed-exitcode   # a resource actually needs to change
$ echo $?
2

$ terraform plan -detailed-exitcode   # re-run immediately after, nothing left to change
$ echo $?
0
```

<SpotTheBug code={`terraform plan -detailed-exitcode -out=$PLAN_FILE
# (workflow never checks $? here at all)`}>
`-detailed-exitcode` มีไว้เจาะจงเพื่อให้ script แยกได้ว่า "มี change จริงพร้อมให้รีวิว" (`2`) กับ "เกิด error จริง" (`1`) กับ "ไม่มีอะไรต้องทำ" (`0`) — พิสูจน์แล้วด้านบน วิธีแก้: จับ `$?` ชัดเจน แยกตามมัน แบบที่บท **[CI/CD for Infrastructure](/terraform-gcp/th/production-and-ecosystem/ci-cd-for-infrastructure/)** ของคอร์สนี้ทำใน pipeline ของมัน
</SpotTheBug>

### เงื่อนไข attribute ของ Workload Identity Federation scope กว้างเกินไป

<Callout title="อ้างอิงจาก docs ไม่ได้รันพิสูจน์">
ไม่มี GCP project ในคอร์สนี้ที่จะสร้าง Workload Identity Pool หรือ provider จริงได้ entry นี้เลยอ้างจาก docs ตรงๆ แทนที่จะรันพิสูจน์จริง — ธรรมเนียมเดียวกับ section Workload Identity Federation ของ **[CI/CD for Infrastructure](/terraform-gcp/th/production-and-ecosystem/ci-cd-for-infrastructure/)** เอง ตาม [คู่มือ OIDC-in-GCP ของ GitHub](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-google-cloud-platform) Workload Identity Pool provider ต้องมี **attribute condition** ที่จำกัดว่า repository/branch ไหนใช้ได้ แล้วให้สิทธิ์ `roles/iam.workloadIdentityUser` บน service account เป้าหมาย scope ตาม principal ของเงื่อนไขนั้น
</Callout>

workflow ที่ generate มามี step `google-github-actions/auth` ที่มี `workload_identity_provider`/`service_account` ที่จริงและรูปทรงถูกต้อง แต่ไม่มีอะไรในโค้ดที่ generate มาของบทนี้แสดง attribute condition ของ provider เองเลย — ส่วนที่ตัดสินใจจริงว่า identity ของ GitHub *ตัวไหน* impersonate service account นั้นได้ Workload Identity Pool provider ที่ไม่มี attribute condition เลย หรือเช็คแค่ repository โดยไม่มี branch/ref เปิดให้ **branch ไหนก็ได้** — รวมถึง pull request จาก fork — impersonate service account ผ่าน pool นี้ได้ วิธีแก้: attribute condition ที่ scope `assertion.ref` ไปที่ branch ที่รัน `apply` จริงเจาะจง แล้วใช้ service account แยกที่ scope แคบกว่า (หรือไม่ใช้เลย) สำหรับ job `plan` ที่รันบน pull request จาก fork ที่ไม่น่าเชื่อถือ

## Mental Model

เก้าใน bug สิบข้อนี้เป็น CI/policy mechanics เดียวกันเป๊ะที่ไม่ขึ้นกับ provider เหมือน review ทั้งสองฝั่งก่อนหน้า — พฤติกรรม `actionlint` เดียวกัน ช่องว่าง `-out`/`-detailed-exitcode` เดียวกัน linter config ที่แยกขาดจาก CI แบบเดียวกัน วิธีแก้ `terragrunt --out-dir` เดียวกัน bug ข้อเดียวที่เฉพาะ GCP จริงๆ คือขอบเขตความไว้ใจ: AWS scope เงื่อนไข `sub` ของ trust policy ของ IAM role, azurerm scope `subject` ของ federated credential ของ App Registration, GCP scope attribute condition ของ Workload Identity Pool provider บน `assertion.ref` — สาม mechanism ต่างกัน แต่รูปแบบความล้มเหลวเหมือนกันเป๊ะเมื่อข้อไหนก็ตามกว้างเกินไป

## ความเข้าใจผิดที่พบบ่อย

- **"ถ้ามีไฟล์ `.tflint.hcl`/checkov config อยู่ใน repo แปลว่ามันถูก enforce"** พิสูจน์แล้วด้านบน: ทั้งสองเครื่องมือ รันตรงกับ `main.tf` ของ pipeline เอง เจอ issue จริงที่ CI run ซึ่งอิงแค่ว่ามี config file อยู่จะไม่เห็นเลย
- **"`actionlint` จับ third-party action ที่ไม่ pin ได้"** พิสูจน์แล้วด้านบน: มันต้องการแค่มี `@ref` อยู่ตาม syntax แต่ไม่แยกแยะ branch name เปลี่ยนแปลงได้แบบ `@master` จาก commit SHA แบบ immutable
- **"การมาสก์ secret ของ GitHub แปลว่า secret แบบ `TF_VAR_*` รั่วผ่าน CI log ไม่ได้"** พิสูจน์แล้วด้านบน: ทันทีที่ secret กลายเป็น environment variable ธรรมดา มันอ่านได้ด้วยเครื่องมือไหนก็ตามที่ dump environment ของมัน
