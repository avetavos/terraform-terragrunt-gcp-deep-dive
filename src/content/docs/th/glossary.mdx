ศัพท์ของคอร์สนี้ครอบคลุมสามชั้น: Terraform core (resource, provider, state, module, plan/apply/destroy) ที่ทำงานเหมือนกันทุก cloud; Terragrunt (unit, dependency, root config, stack) ที่ทำให้หลาย environment ยังคง DRY; และส่วนที่เฉพาะ GCP (generation-based locking ของ gcs backend, google เทียบกับ google-beta, Secret Manager) ที่จะเข้าใจได้ก็ต่อเมื่อรู้ว่ากำลังอ่าน provider ไหนอยู่ เวลาอ่านบทเรียนแล้วเจอคำที่ไม่คุ้น หรือไม่แน่ใจว่ายังใช้ได้อยู่กับ Terraform 1.16 / Terragrunt 1.1 ไหม ให้กลับมาดูที่นี่

## A–B

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| Application Default Credentials (ADC) | ลำดับการค้นหา credential ที่ provider `google`/`google-beta` ใช้เวลาไม่ได้ config `credentials`/service-account key ตรง ๆ — ตอน dev ในเครื่องคือ token จาก `gcloud auth application-default login`; ตอนรันใน GCP/CI ที่มี Workload Identity Federation ก็ใช้ service account ที่แนบไว้ให้เองอัตโนมัติ | [Secrets and Credential Management](/terraform-gcp/th/production-and-ecosystem/secrets-and-credential-management/) |
| apply | `terraform apply` รัน action ทั้งหมดในแผนต่อ infrastructure จริง — เป็นคำสั่งเดียวใน core workflow ที่ create, update หรือ destroy อะไรจริง ๆ; ถ้าไม่มี plan file ที่เซฟไว้ มันจะสร้างให้ก่อนแล้วถาม confirm | [The Terraform Workflow](/terraform-gcp/th/foundations/the-terraform-workflow/) |
| backend | plugin ที่ตัดสินว่า state ของ Terraform เก็บ *ที่ไหน* และ operation ที่ทำกับมันถูก lock ยังไง — config ครั้งเดียวใน block `terraform { backend "gcs" {} }`; เปลี่ยน argument ใน block ต้องรัน `terraform init` ใหม่ (ใส่ `-migrate-state` ถ้าจะย้าย state เดิม) | [Remote Backends and Locking](/terraform-gcp/th/state-management/remote-backends-and-locking/) |

## C

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| Cloud Build (GCP-native CI/CD) | ตัวรัน CI/CD ที่ Google Cloud จัดการให้ config ผ่าน `cloudbuild.yaml` ต่อเข้ากับ resource `google_cloudbuild_trigger` — ทางเลือกแบบ native ของ GCP แทนการรัน `plan`/`apply` ของ Terraform จาก GitHub Actions หรือ CI ภายนอกระบบอื่น | [CI/CD for Infrastructure](/terraform-gcp/th/production-and-ecosystem/ci-cd-for-infrastructure/) |
| catalog / scaffold | `terragrunt catalog` เปิดดู module repository ชุดที่ config ไว้ แล้ว scaffold unit ใหม่จากมันแบบ interactive — เขียน `terragrunt.hcl` กับ `inputs` เริ่มต้นให้เลย แทนที่จะต้องเขียน unit เองตั้งแต่ต้นทุกครั้ง | [Terragrunt HCL and the Root Config](/terraform-gcp/th/terragrunt-fundamentals/terragrunt-hcl-and-the-root-config/) |
| checkov | static-analysis scanner (Bridgecrew/Palo Alto) ที่รันกับ Terraform source *ก่อน* จะ plan เช็ค policy ที่ built-in มาให้ (GCS bucket ที่เปิด public, persistent disk ที่ไม่เข้ารหัส, firewall rule ที่เปิดกว้างเกินไป, …) — รันผ่าน `checkov -d .` หรือ GitHub Action ของมัน ซึ่งต้อง pin ไว้ที่ ref ใดหนึ่ง ไม่ใช้ `@master` เพราะมันเปลี่ยน policy แบบ breaking ได้ทุกครั้งที่ push | [Policy as Code and Static Analysis](/terraform-gcp/th/production-and-ecosystem/policy-as-code-and-static-analysis/) |
| `configuration_aliases` | ประกาศไว้ใน `required_providers` block ของ module ระบุชื่อ provider alias (เช่น `google.us_west1`, `google.us_east1`) ที่ module คาดว่าผู้เรียกจะส่งเข้ามาผ่าน argument `providers = {}` — ถ้าไม่มีตัวนี้ provider ที่ alias ไว้จะข้าม module boundary ไปไม่ได้เลย | [Module Composition and Sources](/terraform-gcp/th/modules/module-composition-and-sources/) |
| `count` | วิธีเก่าแบบใช้ index เพื่อแปลง resource/module block เดียวให้กลายเป็นสำเนาที่เกือบเหมือนกัน N ชุด (`resource.name[0]`, `[1]`, …) — เปราะบางเวลาสลับลำดับ เพราะเอา element กลางออกจาก list จะเลื่อน index ของทุกตัวที่ตามมา ทำให้ resource พวกนั้นถูก destroy แล้วสร้างใหม่ | [Count and For Each](/terraform-gcp/th/variables-and-data-flow/count-and-for-each/) |
| `create_before_destroy` | meta-argument `lifecycle { create_before_destroy = true }` สลับลำดับ replace จาก destroy-ก่อน-แล้ว-ค่อย-create เป็น create-ก่อน — ต้องใช้เมื่อ resource เก่าต้องยังให้บริการ traffic อยู่ หรือยังต้องมีอยู่เพราะอย่างอื่นยัง reference มันจนกว่า resource ใหม่จะพร้อม | [HCL, Providers, and Resources](/terraform-gcp/th/foundations/hcl-providers-and-resources/) |

## D

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| data source | การ lookup แบบ read-only (`data "google_compute_image" "..." {}`) ที่ดึงข้อมูลเกี่ยวกับ resource ที่ Terraform ไม่ได้จัดการ — ไม่ว่าจะเป็นของที่มีอยู่แล้ว (VPC ที่แชร์กัน) หรือค่าที่ provider คำนวณให้ (image family ที่ตรงกับ filter) — และ Terraform จะไม่มีวัน create, update หรือ destroy มันได้เอง | [HCL, Providers, and Resources](/terraform-gcp/th/foundations/hcl-providers-and-resources/) |
| `deletion_policy` | attribute ระดับ resource (`DELETE`/`PREVENT`/`ABANDON`) ที่ resource ของ Google บางตัวมีให้ override พฤติกรรม destroy default ของ provider เอง — อย่าง `google_project` เอง `deletion_policy` ของมัน default เป็น `PREVENT` เลยทำให้ plan ที่จะลบ project fail ออกมาตรง ๆ เว้นแต่จะตั้งเป็น `DELETE` ชัดเจน (หรือ `ABANDON` ที่แค่เอาออกจาก state โดยไม่แตะ project จริง) | [HCL, Providers, and Resources](/terraform-gcp/th/foundations/hcl-providers-and-resources/) |
| `-detailed-exitcode` | flag บน `terraform plan` ที่เปลี่ยน exit code จาก 0/1 ธรรมดา เป็น 0 (ไม่มีอะไรเปลี่ยน), 1 (error) หรือ 2 (มีการเปลี่ยนแปลง) — สิ่งที่ CI pipeline เช็คจริง ๆ เพื่อตัดสินว่า plan ต้องมีขั้นตอน approve จากคนหรือข้ามไปได้เลย | [CI/CD for Infrastructure](/terraform-gcp/th/production-and-ecosystem/ci-cd-for-infrastructure/) |
| dependency / dependencies | block `dependency` ของ Terragrunt อ่าน `outputs` ของอีก unit มาเป็น input (หลังจากรัน `plan`/`apply` ของมันเองก่อน); block `dependencies` (พหูพจน์) แค่การันตีลำดับกับ unit หนึ่งตัวหรือมากกว่าโดยไม่ดึง output ออกมา | [Dependencies Between Units](/terraform-gcp/th/terragrunt-fundamentals/dependencies-between-units/) |
| destroy | `terraform destroy` (หรือ `apply -destroy`) plan แล้ว execute การลบ resource ทุกตัวที่ track อยู่ใน state ตอนนี้ — pipeline plan/apply เดียวกับการเปลี่ยนแปลงปกติ แค่ทุก action ถูกตั้งเป็น `delete` | [The Terraform Workflow](/terraform-gcp/th/foundations/the-terraform-workflow/) |
| drift | ความต่างระหว่างสิ่งที่อยู่ใน state กับสิ่งที่มีอยู่จริงใน GCP — เกิดจากการเปลี่ยนผ่าน console เอง, เครื่องมืออื่น หรือ process นอกระบบ — มีแค่ `terraform plan`/`refresh` เท่านั้นที่เห็นมัน เพราะ Terraform ไม่เคย poll ต่อเนื่องด้วยตัวเอง | [Drift Detection and Import](/terraform-gcp/th/state-management/drift-detection-and-import/) |
| dynamic block | สร้าง nested block ซ้ำ (เช่น `ingress {}` หลายอันในหนึ่ง security group) จาก list หรือ map ตอน runtime — เทียบเท่า `for_each` แต่ใช้กับ nested block บน resource เพราะ nested block ของ resource เองใส่ `for_each` ตรง ๆ ไม่ได้ | [Count and For Each](/terraform-gcp/th/variables-and-data-flow/count-and-for-each/) |

## E–F

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| ephemeral | resource แบบ `ephemeral "..." {}` หรือ variable/output ที่เป็น `ephemeral = true` (Terraform 1.10+) มีอยู่แค่ระหว่าง plan/apply ครั้งเดียว — ไม่ถูกเขียนลง state หรือ plan file เลย — กลไกที่ credential อายุสั้นหรือ password ที่ generate มาไหลผ่านได้โดยไม่ลงดิสก์เลย | [Sensitive Data and Team Workflows](/terraform-gcp/th/state-management/sensitive-data-and-team-workflows/) |
| `error_hook` | hook ของ Terragrunt (ข้างใน `terraform { error_hook "..." {} }`) ที่รันเฉพาะตอนคำสั่ง Terraform ที่ wrap ไว้ fail โดย match กับ error output ด้วย regex ใน `on_errors` — ใช้ทำ cleanup หรือแจ้งเตือนที่ `before_hook`/`after_hook` ธรรมดาทำไม่ได้ | [Terragrunt HCL and the Root Config](/terraform-gcp/th/terragrunt-fundamentals/terragrunt-hcl-and-the-root-config/) |
| `--filter` | flag ปัจจุบันของ Terragrunt สำหรับจำกัดว่า `run --all` จะทำกับ unit ไหนบ้าง (ตาม path, ทิศทาง dependency หรือ query ที่เซฟไว้) — ตัวแทนของคู่เก่าที่ตอนนี้ถูกเอาออกแล้วอย่าง `--terragrunt-include-dir`/`--terragrunt-exclude-dir` | [Running Many Units at Once](/terraform-gcp/th/terragrunt-fundamentals/running-many-units-at-once/) |
| find_in_parent_folders | function `find_in_parent_folders()` ใน block `include` เดินขึ้นจาก directory ของ unit เพื่อหาไฟล์ที่ระบุชื่อไว้ (ปกติคือ `root.hcl`) — กลไกที่ทำให้ทุก unit `include` root config เดียวกันได้โดยไม่ต้อง hardcode relative path ที่จะพังเวลา unit ย้ายที่ | [DRY Configuration with include](/terraform-gcp/th/terragrunt-fundamentals/dry-configuration-with-include/) |
| find / list | `terragrunt find` กับ `terragrunt list` ค้นหา unit ใต้ tree ปัจจุบัน (จะเอาออกมาเป็น JSON หรือกรองตาม dependency ก็ได้) — คำสั่ง discovery แบบ read-only ที่อยู่เบื้องหลัง `--filter` และเบื้องหลัง tooling ของ editor/CI ที่ต้อง enumerate unit โดยไม่ต้องรันอะไรเลย | [Running Many Units at Once](/terraform-gcp/th/terragrunt-fundamentals/running-many-units-at-once/) |
| `for_each` | แปลง resource/module block เดียวให้กลายเป็นหนึ่ง instance ต่อหนึ่ง entry ของ map หรือ set ของ string โดย key ด้วย key ของ map นั้น (`resource.name["prod"]`) แทนที่จะเป็น index ตัวเลข — เอา entry ออกกระทบแค่ instance นั้นตัวเดียว ต่างจาก `count` | [Count and For Each](/terraform-gcp/th/variables-and-data-flow/count-and-for-each/) |
| force-unlock | `terraform force-unlock <lock-id>` เอา state lock ที่ค้างอยู่ออกด้วย ID โดยไม่ต้องรัน plan/apply — ทางออกฉุกเฉินสำหรับ lock ที่ค้างจาก process ที่ crash หรือ CI job ที่ถูกฆ่า และเป็นคำสั่งเดียวที่ถ้าใช้กับ lock ที่ยังถูกถืออยู่จริง ๆ จะทำ state พังได้ | [Remote Backends and Locking](/terraform-gcp/th/state-management/remote-backends-and-locking/) |

## G–I

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| GCS backend `prefix` | สิ่งที่เทียบเท่ากับ `key` ของ S3 backend บน `gcs` backend: path prefix ข้างใน bucket ที่ backend เก็บ state object ไว้ (โดยปกติ Terragrunt ต่อ unit จะใช้หนึ่ง prefix ต่อหนึ่ง unit มากกว่าจะแยก bucket ต่อ unit) | [Remote Backends and Locking](/terraform-gcp/th/state-management/remote-backends-and-locking/) |
| generate | block `generate "..." {}` ของ Terragrunt เขียนไฟล์ (provider block, backend block, version constraint) ลงใน working directory ของ unit ก่อน Terraform จะรัน — กลไกที่ทำให้ทุก unit แชร์ provider/backend boilerplate เดียวกันที่ define ไว้ครั้งเดียวใน `root.hcl` | [Terragrunt HCL and the Root Config](/terraform-gcp/th/terragrunt-fundamentals/terragrunt-hcl-and-the-root-config/) |
| google vs google-beta | provider `google` ครอบคลุม resource/field ที่ GA (generally available) แล้ว; `google-beta` เป็น provider แยกต่างหาก (resource กับ schema เดียวกัน) ที่เพิ่ม field/resource แบบ beta/preview เข้ามาด้วย — resource ที่ใช้ field แบบ beta-only ต้องประกาศ `provider = google-beta` ตรง ๆ ไม่ fallback ให้เองอัตโนมัติ | [HCL, Providers, and Resources](/terraform-gcp/th/foundations/hcl-providers-and-resources/) |
| `google_project_service` | เปิดใช้งาน Google Cloud API ตัวใดตัวหนึ่ง (เช่น `compute.googleapis.com`) บน project — resource ที่ต้องพึ่ง API ที่ provider ส่วนใหญ่คิดว่า "เปิดอยู่แล้ว" ต้องมีตัวนี้เป็น prerequisite ชัดเจน ไม่งั้น `apply` ครั้งแรกจะ fail ด้วย error ว่า API ยังไม่เปิด | [HCL, Providers, and Resources](/terraform-gcp/th/foundations/hcl-providers-and-resources/) |
| HCP Terraform | แพลตฟอร์ม remote-execution ที่ HashiCorp จัดการให้ (เดิมชื่อ Terraform Cloud): รัน `plan`/`apply` บน worker ของตัวเอง, เก็บ state และกั้น apply ไว้หลัง approval กับ Sentinel policy — ทางเลือกแบบ managed แทนการ self-host gcs backend บวก CI pipeline เอง | [CI/CD for Infrastructure](/terraform-gcp/th/production-and-ecosystem/ci-cd-for-infrastructure/) |
| ignore_changes | ข้างใน `lifecycle {}`, `ignore_changes = [tags]` (หรือ list ของ attribute ที่ระบุ) บอก Terraform ให้เลิก report — และเลิก revert — drift เฉพาะ attribute พวกนั้น ใช้บ่อยตอนที่ process อื่น (autoscaling, Lambda ที่ tag ให้) เป็นเจ้าของมันอยู่แล้วจริง ๆ | [Drift Detection and Import](/terraform-gcp/th/state-management/drift-detection-and-import/) |
| import block | block `import { to = ..., id = ... }` แบบ declarative (Terraform 1.5+) เอา resource ที่มีอยู่แล้วเข้ามาอยู่ใต้การจัดการโดยใส่มันไว้ใน `plan`/`apply` ปกติ แทนคำสั่ง `terraform import` แบบเดิมที่เป็น imperative — review ได้ใน PR ก่อนจะมีอะไรเปลี่ยนจริง | [Drift Detection and Import](/terraform-gcp/th/state-management/drift-detection-and-import/) |
| include | block `include "root" { path = find_in_parent_folders() }` ของ Terragrunt ดึง config จากไฟล์ `.hcl` อื่นเข้ามาใน unit ปัจจุบัน รวม `generate`/`remote_state`/`inputs` ของมันเข้าด้วย — กลไก DRY หลัก คู่กับ `dependency` สำหรับ tree ที่มีหลาย unit | [DRY Configuration with include](/terraform-gcp/th/terragrunt-fundamentals/dry-configuration-with-include/) |
| Infracost | ประเมิน cost ต่อเดือนที่เปลี่ยนไปถ้า plan นี้เกิดขึ้นจริง โดยจับคู่ resource ที่วางแผนจะเปลี่ยนกับข้อมูลราคาของ cloud — รันกับ output ของ `terraform show -json` มักถูกโพสต์เป็น PR comment คู่กับ policy-as-code gate | [Policy as Code and Static Analysis](/terraform-gcp/th/production-and-ecosystem/policy-as-code-and-static-analysis/) |

| `terraform_remote_state` | data source ที่อ่าน state ของ config อื่น (พร้อม output ของมัน) ตรง ๆ จาก backend ของมันเลย — เทียบเท่ากับสิ่งที่ block `dependency` ของ Terragrunt ทำผ่าน `mock_outputs` กับการเดินสายที่ generate ให้ แต่เป็น Terraform ธรรมดา | [Remote Backends and Locking](/terraform-gcp/th/state-management/remote-backends-and-locking/) |

| tflint | linter สำหรับ Terraform source ที่จับความผิดพลาดเฉพาะ provider (machine type ที่เลิกใช้แล้ว, string ของ GCP region ที่ผิด) ที่ plan/apply จับไม่ได้ และ `terraform validate` — ซึ่งเช็คแค่ syntax ของ HCL กับความสอดคล้องภายใน — ก็จับไม่ได้เหมือนกัน | [Policy as Code and Static Analysis](/terraform-gcp/th/production-and-ecosystem/policy-as-code-and-static-analysis/) |

## U–W

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| unit | ชื่อของ Terragrunt สำหรับ directory หนึ่งที่มี `terragrunt.hcl` หนึ่งไฟล์ บวก Terraform module ที่มันชี้ไปผ่าน `terraform { source = ... }` — สิ่งที่ `run --all`, `dependency` และ `--filter` ทำงานด้วย เทียบเท่ากับ root module ใน Terraform ธรรมดา | [Terragrunt HCL and the Root Config](/terraform-gcp/th/terragrunt-fundamentals/terragrunt-hcl-and-the-root-config/) |
| validation | block `validation { condition = ..., error_message = ... }` ของ `variable` ปฏิเสธค่าที่ไม่ถูกต้องตอน `plan` พร้อม message ที่กำหนดเอง; ตั้งแต่ Terraform 1.9 condition นี้ reference variable ตัวอื่นได้ด้วย กฎที่ต้องเช็คข้าม variable เลยไม่ต้องหาทางเลี่ยงผ่าน `precondition` อีกต่อไป | [Input Variables](/terraform-gcp/th/variables-and-data-flow/input-variables/) |
| variable | input ที่ตั้งชื่อและมี type ให้ module หรือ root config ให้ค่าผ่าน `.tfvars`, `-var`, environment variable (`TF_VAR_name`) หรือ default — ทางเดียวที่ข้อมูลไหล *เข้า* module จากภายนอก | [Input Variables](/terraform-gcp/th/variables-and-data-flow/input-variables/) |
| version constraint (`~>`) | operator แบบ pessimistic-constraint: `~> 6.66` ยอมรับ `6.66.x` (patch upgrade เท่านั้น) ส่วน `~> 6.0` ยอมรับ `6.x` ทั้งหมด (minor upgrade ด้วย) — วิธีมาตรฐาน pin provider ให้หลวมพอจะได้ bugfix แต่ไม่ได้ major version ที่ breaking | [Module Versioning and Registries](/terraform-gcp/th/modules/module-versioning-and-registries/) |
| Workload Identity Federation (WIF) | กลไก federated identity ของ GCP: workload identity pool + provider เชื่อถือ OIDC issuer ของ CI platform ตัวหนึ่ง ให้ pipeline impersonate service account ผ่าน token อายุสั้นได้ — ตัวแทนมาตรฐานแทนการดาวน์โหลดแล้วเก็บ service-account JSON key ไว้เป็น CI secret | [Secrets and Credential Management](/terraform-gcp/th/production-and-ecosystem/secrets-and-credential-management/) |
| workspace | กลไก built-in ของ Terraform (`terraform workspace new/select`) สำหรับรัน config เดียวกับ state file ที่ตั้งชื่อไว้หลายตัวบน backend เดียวกัน — คอร์สนี้สอน pattern directory-per-environment ของ Terragrunt แทน เพราะ workspace แชร์ backend config กับโค้ดเดียวกันทุก environment แบบเงียบ ๆ ซึ่งมักเป็น tradeoff ที่ผิดสำหรับ prod เทียบกับ non-prod | [Terraform Workspaces](/terraform-gcp/th/multi-environment/terraform-workspaces/) |
| write-only | variable/attribute ที่ marked `write_only = true` (Terraform 1.11+) รับค่าตอน input ได้แต่ไม่เคยถูกเก็บลง state หรือ plan file เลย คู่กับ argument `_version` ที่ต้องขยับเพื่อบอกว่า "ค่า write-only นี้เปลี่ยนแล้ว ส่งใหม่" | [Sensitive Data and Team Workflows](/terraform-gcp/th/state-management/sensitive-data-and-team-workflows/) |
