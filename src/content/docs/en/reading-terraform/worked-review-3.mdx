## The feature

The prompt was: *"Write a GitHub Actions pipeline that runs Terraform plan on pull requests and apply on merge to main, using Workload Identity Federation instead of a stored GCP key, with policy checks."* What follows is the kind of first draft an AI assistant hands back for exactly that prompt — plausible YAML, a real `google-github-actions/auth` action, a Rego policy that reads like every OPA tutorial. It has **10 real bugs**; check the **[AI bug catalog](/terraform-gcp/en/reading-terraform/ai-bug-catalog/)** for the general pattern behind several of them (entries 4, 18, 19, 20, 22). Nine of these ten are identical, provider-agnostic CI/policy mechanics to both sibling reviews' worked review 3 — proven fresh here, in this repo — plus one genuinely GCP-specific Workload Identity Federation bug. This review complements — and links to — **[CI/CD for Infrastructure](/terraform-gcp/en/production-and-ecosystem/ci-cd-for-infrastructure/)**, which shows the corrected pipeline shape in full. Every claim below was proven with real `actionlint`, `tflint`, `checkov`, and `conftest` (via `docker run --rm` against the pinned `rhysd/actionlint`, `ghcr.io/terraform-linters/tflint`, `bridgecrew/checkov`, and `openpolicyagent/conftest` images), plus real Terraform exit codes and a real `terragrunt run --all plan --out-dir`.

## The generated code

```yaml
# .github/workflows/terraform.yml, as generated -- fragment, not a collected fence
name: terraform
on:
  pull_request:
  push:
    branches: [main]

jobs:
  plan:
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/checkout@master
      - uses: hashicorp/setup-terraform@v3
      - name: Authenticate to GCP via Workload Identity Federation
        uses: google-github-actions/auth@v3
        with:
          workload_identity_provider: projects/111122223333/locations/global/workloadIdentityPools/github-pool/providers/github-provider
          service_account: github-actions-terraform@acme-prod-123456.iam.gserviceaccount.com
      - run: terraform init
      - name: plan
        run: |
          echo "TF_VAR_db_password=$TF_VAR_db_password"
          terraform plan -detailed-exitcode -out=$PLAN_FILE
        env:
          PLAN_FILE: tfplan
          TF_VAR_db_password: ${{ secrets.DB_PASSWORD }}

  apply:
    needs: plan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@master
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve
```

## The review walk

### Workflow: `actions/checkout@master` — a mutable branch treated as pinned

**Symptom — real `actionlint`, `rhysd/actionlint`, one-shot container:**

```text
$ docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -color
(no output -- 0 exit code)
```

<SpotTheBug code={`- uses: actions/checkout@master`}>
Same bug as **[AI bug catalog](/terraform-gcp/en/reading-terraform/ai-bug-catalog/)** entry 19, and identical mechanics to both sibling reviews' entry 1 — proven fresh here. `actionlint` only requires *a* `@ref` token to exist syntactically; removing it entirely (`uses: actions/checkout` with no `@` at all) is a real, caught error — confirmed separately: `specifying action "actions/checkout" in invalid format because ref is missing`. But `@master` supplies a syntactically valid ref, so `actionlint` accepts it identically to a pinned commit SHA. Fix: `uses: actions/checkout@<40-char-sha>  # v5.0.0`.
</SpotTheBug>

### Workflow: a shellcheck issue `actionlint` genuinely does catch

**Symptom — real `actionlint` against `run: terraform plan -detailed-exitcode -out=$PLAN_FILE`:**

```text
$ docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -color
.github/workflows/terraform.yml:16:9: shellcheck reported issue in this script: SC2086:info:1:40: Double quote to prevent globbing and word splitting [shellcheck]
   |
16 |         run: |
   |         ^~~~
```

<SpotTheBug code={`run: |
  terraform plan -detailed-exitcode -out=$PLAN_FILE`}>
`actionlint` embeds `shellcheck` against every multi-line `run:` script. `$PLAN_FILE` unquoted is subject to word-splitting and glob expansion by the shell. Fix: `-out="$PLAN_FILE"`.
</SpotTheBug>

### Workflow: `env: TF_VAR_db_password` echoed in a debug line

**Symptom — real, `env` reproducing exactly what a CI runner's environment looks like once `env:` sets a secret-backed variable:**

```text
$ export TF_VAR_db_password="SuperSecret123"
$ env | grep TF_VAR_db_password
TF_VAR_db_password=SuperSecret123
```

<SpotTheBug code={`- name: plan
  run: |
    echo "TF_VAR_db_password=$TF_VAR_db_password"
    terraform plan -detailed-exitcode -out=$PLAN_FILE
  env:
    TF_VAR_db_password: \${{ secrets.DB_PASSWORD }}`}>
GitHub Actions masks a *recognized secret value* in raw log output, but proven above, the plain shell fact underneath is that `TF_VAR_db_password` is a completely ordinary environment variable the moment `env:` sets it. Fix: never echo a secret-backed variable, even for debugging.
</SpotTheBug>

### `apply`: no saved plan — `terraform apply -auto-approve` re-plans from scratch

**Symptom — real, side by side. First, `apply` with no saved plan file:**

```text
$ terraform apply -auto-approve
terraform_data.x: Refreshing state...
Plan: 1 to add, 0 to change, 0 to destroy.
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
```

Then, a real saved plan applied by its file path instead:

```text
$ terraform plan -out=tfplan
$ terraform apply tfplan
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
```

<SpotTheBug code={`- run: terraform init
- run: terraform apply -auto-approve`}>
The `apply` job never downloads the plan the `plan` job computed. Proven above: `apply -auto-approve` with no plan file prints its own fresh `Refreshing state...` / `Plan:` lines — it re-derives a plan from scratch immediately before applying it. Applying a real saved plan file instead prints neither line. Fix: `terraform plan -out=tfplan` as a build artifact in the `plan` job, downloaded and applied verbatim (`terraform apply tfplan`) in the `apply` job.
</SpotTheBug>

### `plan`: `-detailed-exitcode` computed, its three-way exit code never actually read

**Symptom — real, the same command's real exit code in two different states:**

```text
$ terraform plan -detailed-exitcode   # a resource actually needs to change
$ echo $?
2

$ terraform plan -detailed-exitcode   # re-run immediately after, nothing left to change
$ echo $?
0
```

<SpotTheBug code={`terraform plan -detailed-exitcode -out=$PLAN_FILE
# (workflow never checks $? here at all)`}>
`-detailed-exitcode` exists specifically so a script can tell "real changes are ready to review" (`2`) apart from "a real error occurred" (`1`) apart from "nothing to do" (`0`) — proven above. Fix: capture `$?` explicitly and branch on it, the way this course's **[CI/CD for Infrastructure](/terraform-gcp/en/production-and-ecosystem/ci-cd-for-infrastructure/)** lesson's pipeline does.
</SpotTheBug>

### `terraform.tfvars`: a real secret, committed alongside the workflow

```hcl
# terraform.tfvars, as generated
db_password = "Sup3rSecret!2024"
api_token   = "ghp_1234567890abcdefghijklmnopqrstuvwxyz"
```

Same bug as **[AI bug catalog](/terraform-gcp/en/reading-terraform/ai-bug-catalog/)** entry 22 — worse in a CI context specifically, because a committed `.tfvars` ships to every checkout, every fork's pull request, and every CI log that happens to `cat` a file for debugging. Fix: delete the file from the working tree and from git history; source `db_password`/`api_token` exclusively from `TF_VAR_*` environment variables backed by CI secrets.

<SpotTheBug code={`deny[msg] {
  resource := input.resource_changes[_]
  resource.type == "google_compute_instance"

Same bug as **[AI bug catalog](/terraform-gcp/en/reading-terraform/ai-bug-catalog/)** entry 20. Fix:

</SpotTheBug>

### `.tflint.hcl`/checkov: real, working, never wired into CI at all

**Symptom — real `tflint` and `checkov`, one-shot containers, against the pipeline's own `main.tf` (a `google_compute_instance` with a default network, no Shielded VM, no project-wide-SSH-key block, no CSEK encryption):**

```text
$ docker run --rm -v "$(pwd)":/data -w /data ghcr.io/terraform-linters/tflint
1 issue(s) found:

Warning: terraform "required_version" attribute is required (terraform_required_version)

  on main.tf line 1:
   1: terraform {
```

```text
$ docker run --rm -v "$(pwd)":/tf bridgecrew/checkov -d /tf --compact --quiet
Passed checks: 5, Failed checks: 3, Skipped checks: 0

Check: CKV_GCP_38: "Ensure VM disks for critical VMs are encrypted with Customer Supplied Encryption Keys (CSEK)"
FAILED for resource: google_compute_instance.app
Check: CKV_GCP_32: "Ensure 'Block Project-wide SSH keys' is enabled for VM instances"
FAILED for resource: google_compute_instance.app
Check: CKV_GCP_39: "Ensure Compute instances are launched with Shielded VM enabled"
FAILED for resource: google_compute_instance.app
```

<Callout title="A gap in the pipeline, not in the config files shown">
Both tools work correctly and find real issues, proven above — but nothing in the generated CI workflow ever invokes either one. A `.tflint.hcl`/checkov config sitting in the repo, never run by any CI step, provides exactly the same protection as no file at all. Fix: real `tflint` and `checkov` steps in the `plan` job, failing the job on any finding.
</Callout>

### `run --all plan` with no `--out-dir` at the Terragrunt layer

**Symptom — real `terragrunt run --all plan --out-dir`, a real per-unit plan file for every unit in the tree, and the exact next command printed:**

```text
$ terragrunt run --all --non-interactive --no-color --out-dir /tmp/tg-plans -- plan
[live/prod/app] terraform apply "/tmp/tg-plans/live/prod/app/tfplan.tfplan"

❯❯ Run Summary  4 units
   Succeeded    4
```

```text
$ find /tmp/tg-plans -maxdepth 3
/tmp/tg-plans/live/dev/network
/tmp/tg-plans/live/dev/app
/tmp/tg-plans/live/prod/network
/tmp/tg-plans/live/prod/app
```

<SpotTheBug code={`terragrunt run --all -- plan
# ... later, in a separate job/step ...
terragrunt run --all -- apply -auto-approve`}>
Exactly the same bug as the plain-Terraform "no `-out`" entry above, one layer up. Fix: `run --all plan --out-dir <dir>` in the `plan` job, `run --all apply --out-dir <dir>` (the same directory) in the `apply` job.
</SpotTheBug>

### Workload Identity Federation's attribute condition scoped too broadly

<Callout title="Docs-sourced, not run-proven">
No GCP project exists in this course to create a real Workload Identity Pool or provider in, so this entry is quoted directly rather than reproduced live — same convention as **[CI/CD for Infrastructure](/terraform-gcp/en/production-and-ecosystem/ci-cd-for-infrastructure/)**'s own Workload Identity Federation section. Per [GitHub's OIDC-in-GCP guide](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-google-cloud-platform), a Workload Identity Pool provider needs an **attribute condition** restricting which repository/branch can use it, then a grant of `roles/iam.workloadIdentityUser` on the target service account scoped to that condition's principal.
</Callout>

The generated workflow's `google-github-actions/auth` step with `workload_identity_provider`/`service_account` is real and correctly-shaped, but nothing in this lesson's generated code shows the provider's own attribute condition — the part that actually decides *which* GitHub identities may impersonate that service account. A Workload Identity Pool provider with no attribute condition, or one that only checks the repository without the branch/ref, lets **any** branch — including a pull request from a fork — impersonate the service account through the pool. Fix: an attribute condition scoping `assertion.ref` to the exact branch that runs `apply`, and a separate, more narrowly-scoped service account (or none at all) for the `plan` job that runs on pull requests from untrusted forks.

## Mental Model

Nine of these ten bugs are identical, provider-agnostic CI/policy mechanics to both sibling reviews — the same `actionlint` behaviors, the same `-out`/`-detailed-exitcode` gaps, the same disconnected linter configs, the same `terragrunt --out-dir` fix. The one genuinely GCP-specific bug is the trust boundary: AWS scopes an IAM role's trust policy `sub` condition, azurerm scopes an App Registration's federated credential `subject`, GCP scopes a Workload Identity Pool provider's attribute condition on `assertion.ref` — three different mechanisms, identical failure mode when any of them is too broad.

## Common Misconceptions

- **"If a `.tflint.hcl`/checkov config file exists in the repo, it's being enforced."** Proven above: both tools, run directly against the pipeline's own `main.tf`, found real issues that a CI run relying only on the config files' presence would never see.
- **"`actionlint` catches unpinned third-party actions."** Proven above: it requires *a* `@ref` to exist syntactically, but does not distinguish a mutable branch name like `@master` from an immutable commit SHA.
- **"GitHub's secret masking means a `TF_VAR_*` secret can't leak through CI logs."** Proven above: the moment a secret becomes a plain environment variable, it is readable by any tool that dumps its environment.

<Callout title="The one-line takeaway">
A CI pipeline's real safety comes from what actually runs, in order, on the actual artifact — not from a policy file existing, a tool being installed, or a flag being present in a command. Nine of these ten gaps are identical to both sibling reviews regardless of cloud; the tenth — where the trust boundary actually lives — is the one place GCP's shape genuinely differs, through a Workload Identity Pool's attribute condition rather than a trust policy or federated credential.
