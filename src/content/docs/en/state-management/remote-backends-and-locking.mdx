## The idea in one sentence

A **remote backend** stores state in a shared location like Cloud Storage instead of on one person's laptop, and **locking** stops two people from writing to that shared state at the same time.

## Why local state does not work for a team

By default, `terraform.tfstate` lives on the machine where you ran `apply`. That is fine for a solo experiment, but it breaks down the moment a second person joins:

- Teammate A runs `apply` and creates a VPC network. Their laptop's local state file now knows about it.
- Teammate B, on a different laptop, has never seen that state file. They run `plan` against their own stale or empty local state and either try to recreate the VPC network or get a plan that makes no sense next to what actually exists.
- CI/CD pipelines have the same problem in a sharper form — a pipeline runner is a fresh, disposable environment with no local state file at all. It needs a canonical copy of state to read from and write to on every run, not a copy that happens to be sitting on someone's laptop.

The fix is to move state off any individual machine and into a shared backend that every team member and every CI run points at.

## Configuring the GCS backend

The standard way to store Terraform state on Google Cloud is a Cloud Storage bucket configured as the backend:

```hcl
terraform {
  backend "gcs" {
    bucket = "my-company-terraform-state"
    prefix = "networking/state"
  }
}
```

The bucket must already exist before you point a backend at it — Terraform will not create it for you. `bucket` names the Cloud Storage bucket, and `prefix` is the path within that bucket under which this configuration's state object is stored, so different configurations (or different Terragrunt units) typically use different prefixes in the same bucket.

Notice there is no locking argument to set. Per the GCS backend's own documentation, "this backend supports state locking" — full stop; unlike the S3 backend page (which names `use_lockfile` and a `<key>.tflock` object) or the azurerm page (which names the blob-lease mechanism), the GCS backend page does not spell out the underlying mechanism. Worth stating plainly rather than guessing at an implementation detail no fetched HashiCorp page confirms. What is confirmed either way: there is no separate lock table to create, no extra argument to flip on, and no additional GCP resource to pay for and keep in sync with the state bucket — locking is a property of the backend against the same bucket, with nothing extra to provision. This is genuinely simpler than the locking story on some other clouds, where a separate locking resource has historically had to be provisioned alongside the state bucket.

It is still worth turning on Object Versioning on the state bucket itself. Versioning is not what provides locking — locking works regardless — but it gives you a recovery path if a bad `apply` overwrites state with something you did not want.

## Migrating a backend: `init -migrate-state` vs `init -reconfigure`

Changing the `backend` block — moving to a different bucket, changing `prefix`, or moving from local to `gcs` for the first time — requires re-running `terraform init`, and Terraform gives you two different flags depending on whether you want the old state carried over. No cloud credentials exist in this course, so the proof below changes a **local** backend's `path` rather than migrating to GCS — the exact same prompt and mechanics apply to a local→GCS move, only the backend type differs.

`terraform init -migrate-state` asks whether to copy existing state into the new backend location. Real output, changing `path = "state/old.tfstate"` to `path = "state/new.tfstate"` in a `backend "local"` block:

```text
$ terraform init -migrate-state
Initializing the backend...
Backend configuration changed!

Terraform has detected that the configuration specified for the backend
has changed. Terraform will now check for existing state in the backends.
Do you want to copy existing state to the new backend?
  Pre-existing state was found while migrating the previous "local" backend to the
  newly configured "local" backend. No existing state was found in the newly
  configured "local" backend. Do you want to copy this state to the new "local"
  backend? Enter "yes" to copy and "no" to start with an empty state.

  Enter a value: yes

Successfully configured the backend "local"! Terraform will automatically
use this backend unless the backend configuration changes.
```

Answering `yes` really copies the resource into the new location — `state/new.tfstate` contains the same `local_file` resource the old path had. `terraform init -reconfigure` skips that prompt entirely and does **not** carry state over — proof, changing the `path` again and running `-reconfigure` instead:

```text
$ terraform init -reconfigure
Initializing the backend...

Successfully configured the backend "local"! Terraform will automatically
use this backend unless the backend configuration changes.
```

No migration question at all. The next `plan` proves the difference — Terraform now believes the resource does not exist, because the new backend location was never populated:

```text
$ terraform plan
  # local_file.config will be created
  + resource "local_file" "config" {
      + content  = "listen=8080\n"
      + filename = "./generated/app.conf"
    }

Plan: 1 to add, 0 to change, 0 to destroy.
```

`-reconfigure` is for "start clean at this new location, I do not want the old state" (or the old backend is gone/unreachable); `-migrate-state` is for "this is the same infrastructure, just move where its state record lives." Picking the wrong one against a real GCS bucket either leaves the old state behind unmigrated, or (worse) makes Terraform think a running VPC network needs to be recreated from scratch.

## Partial backend configuration with `-backend-config`

A `backend` block does not have to hardcode every argument — leaving it empty and supplying values at `init` time (from a file or individual `-backend-config="key=value"` flags) keeps per-environment values out of committed `.tf` files:

```hcl
terraform {
  backend "gcs" {}
}
```

```text
# backend.hcl (not committed, or generated by CI per environment)
bucket = "my-company-terraform-state"
prefix = "networking/state"
```

```bash
terraform init -backend-config=backend.hcl
```

Real output against a local backend proving the flag is accepted and merged (`path` supplied the same way as `bucket`/`prefix` would be for GCS):

```text
$ terraform init -backend-config=backend.hcl
Initializing the backend...

Successfully configured the backend "local"! Terraform will automatically
use this backend unless the backend configuration changes.
```

This is exactly the mechanism CI pipelines use to point the same configuration at a different GCS bucket or prefix per environment (`dev.hcl`, `prod.hcl`) without duplicating the `.tf` files.

## `terraform force-unlock`: the manual escape hatch

If an `apply` is killed mid-run (a laptop sleeps, a CI job is cancelled), the lock it acquired can be left behind with nothing left running to release it. `terraform force-unlock <LOCK_ID>` removes that lock manually. Real `-help` output from Terraform 1.16.4:

```text
$ terraform force-unlock -help
Usage: terraform [global options] force-unlock LOCK_ID

  Manually unlock the state for the defined configuration.

  This will not modify your infrastructure. This command removes the lock on the
  state for the current workspace. The behavior of this lock is dependent
  on the backend being used. Local state files cannot be unlocked by another
  process.

Options:

  -force                 Don't ask for input for unlock confirmation.
```

The `LOCK_ID` is not something you invent — when a lock is already held, the *next* run that fails to acquire it prints the lock's ID (and who holds it, and when it was acquired) in its own error message, and that ID is what you paste into `force-unlock`. **A stale lock genuinely cannot be produced offline in this course** — the local backend the harness uses has no lock to leave behind the way a GCS-backed lock can (the `-help` text above says exactly that: "Local state files cannot be unlocked by another process"). Treat `force-unlock` as a last resort for a lock you have independently confirmed is stale (the process that held it is actually gone — check first, e.g. that the CI run really did get cancelled), never a reflex for "my apply is being slow."

## Terragrunt: `remote_state` generates the `backend.tf` you never hand-write — and proves `project`/`location` are not part of it

Terragrunt's `remote_state` block in `root.hcl` generates the exact `backend` block above for every unit that includes it, resolving `prefix` per-unit with `path_relative_to_include()`. The GCS backend is the one where it matters most to prove exactly which config keys land in the generated file, because `remote_state` also accepts `project` and `location` to **auto-create the bucket** if it does not exist yet:

```hcl
# root.hcl
remote_state {
  backend = "gcs"
  generate = {
    path      = "backend.tf"
    if_exists = "overwrite"
  }
  config = {
    project  = "my-gcp-project-id"
    location = "us-central1"
    bucket   = "my-company-terraform-state"
    prefix   = "${path_relative_to_include()}"
  }
}
```

```hcl
# network/terragrunt.hcl
include "root" {
  path = find_in_parent_folders("root.hcl")
}

terraform {
  source = "."
}
```

Running `terragrunt run -- init -backend=false` in the `network` unit generates the real `backend.tf` — and it proves the point directly: `project` and `location` do **not** appear in it at all, only `bucket` and the resolved `prefix`:

```text
# Generated by Terragrunt. Sig: nIlQXj57tbuaRZEa
terraform {
  backend "gcs" {
    bucket = "my-company-terraform-state"
    prefix = "network"
  }
}
```

`project` and `location` were consumed by Terragrunt itself, at the step where it checks whether the bucket exists and creates it if not (`disable_init = false`, the default) — they have no equivalent field in a `gcs` backend block's own schema, so generating them into `backend.tf` would produce an invalid backend configuration. This is the opposite of the AWS/azurerm case (`state-management/remote-backends-and-locking.mdx`'s AWS version), where every `config` key is a real backend argument and lands in the file verbatim — GCP's `remote_state` block is doing two jobs (bucket bootstrap plus backend generation) with two different key sets, and only one of those sets is backend syntax.

## What locking actually prevents

Imagine locking did not exist. Two people, or a person and a CI run, both execute `terraform apply` against the same GCS-backed state at nearly the same moment. Both read the current state, both compute a plan, and both start writing their results back to the same state object. Depending on timing, the second write can overwrite the first — silently dropping the first run's recorded changes even though the first run's infrastructure changes actually happened — or the state file can end up corrupted mid-write.

A lock turns that race into a queue. The first `apply` to start acquires the lock; the second `apply` either waits for the lock to be released, or fails immediately with a clear "state is locked" error, depending on the flags used. Either way, the second run does not get to write over the first run's state while it is mid-flight.

```bash
# A run that finds the state already locked fails fast with a clear message,
# rather than corrupting the state file
terraform apply
# Error: Error acquiring the state lock
```

## Mental Model

Every mechanism in this lesson exists to answer one question honestly: "whose write wins, and does the loser find out?" A shared backend answers "where is the one true copy" so nobody's laptop is that copy. Locking answers "what happens when two writes race" by turning the race into a queue instead of a coin flip — proven above, GCS's own backend page confirms locking is supported without over-claiming a mechanism no page actually documents. `-migrate-state` vs `-reconfigure` answers "does the old record follow me" when the backend's location changes. `force-unlock` exists only because the queue mechanism itself can jam (a lock holder that will never release) — it is a manual override of the queue, not a replacement for it. And GCP's `remote_state` block does two genuinely different jobs at once (bootstrap the bucket, generate the backend config) — conflating their two key sets is exactly the kind of mistake real `terragrunt render` output catches immediately.

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| GCS backend's built-in locking | No separate lock table or extra argument to provision (proven above via the backend's own docs) | The exact mechanism is not documented on the page itself — worth stating as a real gap rather than inventing one |
| `-migrate-state` over `-reconfigure` when the backend location changes | Old state is carried forward — proven above, the resource is still tracked afterward | Requires answering an interactive prompt (or `-input=false` plus care) — easy to fat-finger "no" and lose the link to existing infrastructure |
| `remote_state`'s `project`/`location` auto-creating the bucket | One block bootstraps infrastructure and generates the backend config together | Those two keys are silently absent from the generated `backend.tf` (proven above) — easy to assume, wrongly, that they are real backend arguments |
| Partial backend config (`-backend-config`) | Keeps environment-specific values out of committed `.tf` files | The backend block alone, read in isolation, no longer tells you which bucket/prefix state actually lives in — you must also find the `-backend-config` file or CI step |

## Common Misconceptions

- **"`terraform init -reconfigure` is just a safer alias for `-migrate-state`."** Proven above: `-reconfigure` never prompts and never copies state — the very next `plan` shows the tracked resource as "to create" again, because the new backend location was never populated.
- **"A stale lock is common and `force-unlock` is a routine command."** Proven above via the real `-help` text: it is a manual escape hatch for a lock whose holder is confirmed gone, not a default response to a slow or in-progress `apply`.
- **"GCS locking works through object generation numbers and versioning, the same way object versioning works."** No fetched HashiCorp documentation page actually states this mechanism — the honest answer, proven above, is that the docs confirm locking is supported without detailing how; asserting the mechanism as fact is exactly the kind of unverifiable claim this course avoids.
- **"`remote_state`'s `project` and `location` end up in the generated `backend.tf`, since they're in the same `config` map as `bucket`/`prefix`."** Proven above with real generated output: only `bucket` and `prefix` appear. `project`/`location` are consumed entirely by Terragrunt's own bucket-bootstrap step and have no equivalent field in the `gcs` backend block's schema.

## Reading AI-generated code

When reviewing generated backend configuration or migration scripts, check for:

- A confident, specific claim about how GCS implements backend locking internally (object generation numbers, a specific precondition mechanism) presented as fact — proven above, no fetched HashiCorp page documents the mechanism; state that gap rather than inventing a plausible internal.
- `terraform init -reconfigure` used in a runbook step that is supposed to preserve existing state — proven above, `-reconfigure` does not migrate state at all; the correct flag for that intent is `-migrate-state`.
- A CI script that pipes `yes` into every `terraform init` unconditionally to avoid interactive prompts, including the `-migrate-state` "copy existing state?" prompt — that answer needs to be a deliberate `yes` (this environment really is a location change) or the script risks silently copying state into the wrong place.
- `force-unlock` called with a made-up or copy-pasted-from-a-tutorial lock ID rather than the one printed in the actual "state is locked" error for the run in question.
- A Terragrunt `remote_state` block whose generated `backend.tf` is assumed to contain `project`/`location` (because they're in the same `config` map) — proven above, they are silently dropped; any downstream tooling that tries to read them out of the generated file will find nothing there.

<SpotTheBug code={`# CI "cleanup" step run before every apply, to avoid ever seeing a locked-state error
terraform force-unlock -force $(cat last-known-lock-id.txt)
terraform apply -auto-approve`}>
This runs `force-unlock` unconditionally before every `apply`, using a lock ID cached from some previous run rather than the ID of any lock that actually exists right now. Proven above: `force-unlock` "will not modify your infrastructure" by itself, but blindly releasing a lock that is currently, legitimately held — by a teammate's in-progress `apply`, or a concurrent CI run — removes the one protection state locking provides. The next line's `apply` can now race directly against whatever was holding that lock, which is precisely the corrupted-write scenario locking exists to prevent. The correct use of `force-unlock` is reactive and manual: read the actual "state is locked" error for the ID it names, confirm independently that the holder is gone, and only then unlock that specific ID — never a pre-emptive step in a script that runs regardless of whether anything is actually locked.
</SpotTheBug>
