## The idea in one sentence

A **module** is just any directory of `.tf` files — the one you run `terraform apply` in is the **root module**, and any directory you call into with a `module` block is a **child module**, so there is nothing structurally special about "being a module."

## There is no module keyword — only usage

This trips people up the first time they hear it: Terraform has no special file, no `module.tf`, no magic marker that turns a directory into a module. Every directory of `.tf` files you have ever written is already a module. The directory where you run `terraform init` and `terraform apply` directly is called the **root module**. The moment you reference some other directory of `.tf` files from inside a `module` block, that other directory becomes a **child module** — but its own `.tf` files look exactly the same as any root configuration's:

```hcl
# root main.tf — calling a child module
module "bucket" {
  source      = "./modules/gcs-bucket"
  bucket_name = "acme-app-logs"
}
```

That is the entire distinction: a child module is a directory of Terraform configuration that some other configuration references by address. Nothing inside the module's own `.tf` files has to change to make this true — the same directory could be applied directly as a root module if you `cd` into it and ran `terraform apply` there yourself.

## Why a module's file layout mirrors a root config

Because a module is a Terraform configuration, it follows the exact same three-file convention you already use for root configs, just with a different audience in mind:

- **`variables.tf`** — the module's inputs. This is its public API surface: what a caller must or may provide.
- **`main.tf`** — the resources the module actually manages.
- **`outputs.tf`** — the values the module exposes back to whoever called it.

This is worth internalizing: a module is not a special templating construct layered on top of Terraform. It is a normal Terraform configuration that happens to be parameterized by `variables.tf` on the way in and by `outputs.tf` on the way out.

```hcl
# modules/gcs-bucket/variables.tf
variable "bucket_name" {
  description = "Name of the GCS bucket to create"
  type        = string
}

variable "project_id" {
  description = "ID of the GCP project that owns the bucket"
  type        = string
}
```

```hcl
# modules/gcs-bucket/main.tf
resource "google_storage_bucket" "this" {
  name     = var.bucket_name
  project  = var.project_id
  location = "US"
}
```

```hcl
# modules/gcs-bucket/outputs.tf
output "url" {
  description = "GS URI of the created bucket"
  value       = google_storage_bucket.this.url
}
```

A caller wires this up with a `module` block, treating `bucket_name` and `project_id` as the inputs and `module.<name>.url` as the output it can reference elsewhere:

```hcl
# root main.tf
module "logs_bucket" {
  source      = "./modules/gcs-bucket"
  bucket_name = "acme-app-logs"
  project_id  = "acme-app-prod"
}

output "logs_bucket_url" {
  value = module.logs_bucket.url
}
```

## Designing a module with one clear responsibility

The single biggest design mistake with modules is scope creep: a module that starts as "a VPC network" and slowly grows an IAM binding here, a Compute Engine instance there, a Cloud Function somewhere else, until nobody can reuse it for anything but the one thing it was originally built for. Aim for a module that does one well-scoped job — "a VPC network with public and private subnets," not "all of our GCP networking, IAM, and compute."

Two practical habits keep a module reusable instead of accidentally specific to one caller:

- **Sensible defaults for optional inputs.** If most callers want the same value for an input, give that input a `default` in `variables.tf` so a simple caller does not have to specify it at all.
- **Resist over-parameterizing on day one.** It is tempting to expose every field a resource supports as a variable "just in case." Every variable you add is a permanent piece of the module's public API that you now have to document and maintain. Add an input when a real caller actually needs that variation — not preemptively for a hypothetical one.

```hcl
# modules/gcs-bucket/variables.tf
variable "bucket_name" {
  description = "Name of the GCS bucket to create"
  type        = string
}

variable "project_id" {
  description = "ID of the GCP project that owns the bucket"
  type        = string
}

variable "force_destroy" {
  description = "Allow bucket to be destroyed even if it still contains objects"
  type        = bool
  default     = false
}
```

Here `force_destroy` has a sensible default — most callers never touch it — while `bucket_name` has none, because every caller genuinely needs a different bucket name and there is no reasonable default to guess.

## The rule a reusable module must follow: never declare your own provider

A module intended for reuse should almost never contain a `provider` block with real configuration in it. Per the official guidance (`developer.hashicorp.com/terraform/language/modules/develop/providers`): "Modules intended for use by other modules should not contain `provider` blocks. Modules with their own provider configurations are incompatible with arguments like `for_each`, `count`, and `depends_on`." That is not a style preference — it is enforced, with a real error. Proof: a child module with a genuine, non-empty `provider "google" { project = "my-project-id" }` block, called with `count`:

```hcl
# @expect-error Module is incompatible with count, for_each, and depends_on
terraform {
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 8.0"
    }
  }
}

provider "google" {
  project = "my-project-id"
}

resource "google_storage_bucket" "this" {
  name     = "acme-example-bucket"
  location = "US"
}
```

```hcl
# @expect-error Module is incompatible with count, for_each, and depends_on
module "bucket" {
  source = "./modules/bucket"
  count  = 2
}
```

Real `terraform init` output on Terraform 1.16.4:

```text
$ terraform init
Error: Module is incompatible with count, for_each, and depends_on

  on main.tf line 12, in module "bucket":
  12:   count  = 2

The module at module.bucket is a legacy module which contains its own local
provider configurations, and so calls to it may not use the count,
for_each, or depends_on arguments.

If you also control the module "./modules/bucket", consider updating this
module to instead expect provider configurations to be passed by its
caller.
```

This is the exact same error text — and the exact same current-version-vs-older-docs-wording mismatch — proven identically in the aws and azurerm siblings of this course, because it is a core Terraform language rule, not something google-specific. The fix is `configuration_aliases`: the module declares it needs a provider passed in under a local alias, and never configures one itself.

```hcl
# Fixed: modules/bucket/main.tf never owns a provider block
terraform {
  required_providers {
    google = {
      source                = "hashicorp/google"
      version               = "~> 8.0"
      configuration_aliases = [google.this]
    }
  }
}

resource "google_storage_bucket" "this" {
  provider = google.this
  name     = "acme-example-bucket"
  location = "US"
}
```

```hcl
# Fixed: root main.tf passes the provider explicitly
module "bucket" {
  source = "./modules/bucket"
  count  = 2
  providers = {
    google.this = google
  }
}
```

Real `terraform validate` output after the fix (`plan` for `google_storage_bucket` needs a real GCP project, so this course validates rather than plans it):

```text
$ terraform validate
Success! The configuration is valid.
```

`providers = {}` in the calling `module` block is how the caller hands the module a specific (possibly aliased) provider configuration explicitly, instead of the module silently inheriting the default provider the way it would if it declared no `provider` block and no `configuration_aliases` at all. A module written this way works identically whether it is called once, with `count`, or with `for_each` — because it never owns a provider configuration to begin with.

## Mental Model

A module is reusable in direct proportion to how little it assumes about its caller. File layout, sensible defaults, and resisting over-parameterization all serve that goal at the *configuration* level; the provider rule proven above serves it at the *provider* level — a module that owns its own `provider` block has quietly assumed "I will only ever be called once, with the default provider," and that assumption becomes a real, named error the instant a caller tries `count`, `for_each`, or `depends_on`. `configuration_aliases` plus a caller-side `providers = {}` map is how a module states its provider dependency explicitly instead of assuming it.

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| One clear responsibility per module | Reusable across many callers without modification | More modules to navigate; a caller may need to wire several together (covered in `module-composition-and-sources.mdx`) |
| Sensible defaults on optional inputs | Simple callers need only the required inputs | A default can hide a real decision a caller should have made consciously |
| `configuration_aliases` instead of an owned `provider` block | Works with `count`/`for_each`/`depends_on` — proven above, the alternative hard-fails with a real error | The caller must remember to pass `providers = {}`; forgetting it is its own error to debug |

## Common Misconceptions

- **"A module needs its own `provider` block to know which GCP project to use."** Proven above: the opposite is true for a reusable module — an owned provider block is exactly what makes `count`/`for_each`/`depends_on` fail with a real, named error. The project should come from the caller.
- **"The count/for_each restriction on modules with providers is just a style lint, not a hard error."** Proven above with a real `terraform init` failure on Terraform 1.16.4: "Module is incompatible with count, for_each, and depends_on."
- **"This is a google-provider-specific quirk."** Proven above by exact-text comparison across this course's three sibling repos: the aws, azurerm, and google providers all produce the identical Terraform-core error text, because the restriction lives in Terraform itself, not in any one provider.
- **"You can always trust an error message's exact wording from memory or from a docs page you read a while ago."** Proven above: the officially documented example text ("Module does not support count ... contains a nested provider configuration") does not match the real Terraform 1.16.4 output ("Module is incompatible with count, for_each, and depends_on") — always re-verify against the pinned version.

## Reading AI-generated code

When reviewing a generated module intended to be reusable, check for:

- A `provider` block with real, non-empty arguments inside a module directory — proven above, this silently breaks the moment a caller tries `count`, `for_each`, or `depends_on` on that module, often far from where the provider block was originally written.
- A module that hardcodes a GCP project ID, region, or credential-adjacent setting instead of accepting it (or an aliased provider) from its caller.
- Every field a resource supports exposed as a module variable "for completeness," rather than added when a real caller needs that specific variation — proven above, each one is a permanent piece of public API to maintain.
- A required variable with no `description`, making the module's public API harder for a caller to use correctly without reading the resource block itself.

<Callout title="The one-line takeaway">
A **module** is nothing more than a directory of `.tf` files; the directory you `apply` directly is the **root module**, and any directory referenced through a `module` block becomes a **child module** — there is no special syntax involved. Because a module is a full Terraform configuration, it follows the same **`variables.tf` / `main.tf` / `outputs.tf`** convention as a root config, just with `variables.tf` acting as its public inputs and `outputs.tf` as what it exposes back to the caller. Good module design means one clear responsibility, sensible **defaults** for optional inputs, and adding new variables only when a real caller needs the variation rather than over-parameterizing preemptively. A reusable module must also never own a real `provider` configuration — proven above with a real error, identical across all three clouds' providers because it is a Terraform-core rule — use `configuration_aliases` and let the caller pass `providers = {}` instead.
</Callout>
