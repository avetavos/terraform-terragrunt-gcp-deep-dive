## What this module is for

Every earlier module in this course taught you to *use* Terraform and Terragrunt: writing HCL, running `init`/`plan`/`apply`, storing state remotely, wiring variables and modules, building a multi-environment live tree, and shipping through CI with policy checks. None of it required knowing what `terraform plan` actually *builds* before it prints a diff, what `terraform.tfstate` actually *is* at the byte level, what `-out=tfplan` actually writes to disk, how `hashicorp/google` (or `aws`, or `azurerm`) actually talks to `terraform` as a *process*, or how `terragrunt run --all` actually decides which unit runs before which.

That gap is exactly where AI-generated Terraform tooling and reviews fail in ways that look fine on the surface: a "policy check" script that greps `terraform plan` text output instead of reading the structured `resource_changes[].change.actions` array `terraform show -json` actually produces; a CI step that assumes `terraform apply -parallelism=50` is always faster with no idea what the flag bounds; a teammate who "fixes" a stuck state lock by hand-editing `terraform.tfstate`'s `serial` field, not knowing `state push` will simply refuse a stale one; a `dev_overrides` block copy-pasted from a blog post that silently breaks `init` for a reason nobody can explain from the error text alone. None of these are HCL syntax errors. None of them are caught by `terraform validate`. All of them are facts about the runtime this module makes provable.

This module has one job: give you five pieces of runtime knowledge that let you look at **any** Terraform or Terragrunt output — a graph, a state file, a `-out` plan, a provider crash, a `run --all` log — and know exactly what produced it and why.

1. **What does `terraform plan`/`apply` actually walk, and in what order?** ([The Graph and the Walk](/terraform-gcp/en/terraform-internals/the-graph-and-the-walk/) — a real `terraform graph`, DOT and Mermaid, `-parallelism`, `depends_on` vs implicit references)
2. **What is `terraform.tfstate`, really, at the schema level?** ([State File Anatomy](/terraform-gcp/en/terraform-internals/state-file-anatomy/) — real `state pull` JSON, `serial`/`lineage` enforcement proven with a real refusal, `state replace-provider`, `show -json` vs raw state)
3. **What is a saved plan file, and what does CI/policy tooling actually read from it?** ([Plan File and JSON Output](/terraform-gcp/en/terraform-internals/plan-file-and-json-output/) — `-out` is a real zip, proven with `unzip -l`; the full `resource_changes[].change.actions` matrix; `-detailed-exitcode`)
4. **How does Terraform actually talk to a provider?** ([Provider Plugin Protocol](/terraform-gcp/en/terraform-internals/provider-plugin-protocol/) — go-plugin over gRPC, a real `TF_LOG=TRACE` handshake and `GetProviderSchema` call, why `init` downloads a binary per OS/arch, a real induced provider crash, `dev_overrides`)
5. **How does Terragrunt decide what to run, and in what order?** ([Terragrunt Discovery and DAG](/terraform-gcp/en/terraform-internals/terragrunt-discovery-and-dag/) — real `terragrunt find`/`list --dag`, a real `run --all --parallelism 1` ordered log, `.terragrunt-cache`, `mock_outputs`)

Every claim in this module is backed by one of three things: a real, reproduced local run against **Terraform 1.16.4** and **Terragrunt 1.1.0** (this course's pinned versions) — pasted below the claim, trimmed of machine-specific paths but never invented; the official docs at [developer.hashicorp.com](https://developer.hashicorp.com/terraform) or [terragrunt.gruntwork.io](https://terragrunt.gruntwork.io); or, where neither is possible offline, an explicit note saying so.

<Callout title="The one-line takeaway">
This module doesn't add new HCL — it explains the five mechanisms every `plan`, `apply`, `state`, and `run --all` you have already typed actually runs through: the **graph** (a DOT/Mermaid-renderable dependency graph Terraform builds from your configuration, then walks with up to `-parallelism` concurrent nodes — default **10**, proven below with real wall-clock timing), **state** (a versioned JSON document — `version`, `serial`, `lineage`, per-resource `schema_version` — that a real `state push` refuses to overwrite with anything older or unrelated), the **plan file** (`-out` writes a real zip containing the plan, the prior and post-refresh state, and a snapshot of your config, and `show -json` turns it into the exact `resource_changes[].change.actions` array policy tooling like Conftest/OPA reads), the **provider plugin protocol** (every provider is a separate binary Terraform starts as a subprocess and talks to over gRPC — protocol version 5 or 6 — with a real, visible handshake under `TF_LOG=TRACE`), and **Terragrunt's own DAG** (built from `dependency`/`dependencies` blocks across a live tree, independent of Terraform's own graph, and walked with its own `--parallelism`).
</Callout>

## Mental Model

Everything in this module is one story told from five different points on the same pipeline: **Terraform never executes your configuration top to bottom — it compiles it into a graph, and every command (`plan`, `apply`, `destroy`, `graph` itself) is a walk over that graph, dispatching each node to whichever provider plugin owns it over gRPC, and recording the result in one versioned state document.** Terragrunt sits one layer above this and does the same thing at a coarser grain: instead of resources, its nodes are whole Terraform units (directories), its edges come from `dependency`/`dependencies` blocks instead of resource references, and its own `--parallelism` bounds how many *units* run concurrently — completely independent of the `-parallelism` any individual `terraform apply` inside a unit uses. Once you can place any fact in this module against "graph, walk, gRPC call, state write" (and, one layer up, "Terragrunt's own graph, walk, unit run"), reading an unfamiliar `plan` diff, a `state` file, a CI policy step, or a `run --all` log stops being five separate mysteries.

## Common Misconceptions

- **"`terraform apply` runs resources in the order they're written in the file."** [The Graph and the Walk](/terraform-gcp/en/terraform-internals/the-graph-and-the-walk/) proves the opposite with a real `terraform graph`: order comes entirely from the dependency graph (implicit references and explicit `depends_on`), and independent resources are dispatched concurrently, up to `-parallelism` (default 10) — proven with real wall-clock timing showing 5 independent 2-second operations finish in ~2s by default and ~10s at `-parallelism=1`.
- **"State is just a cache; you can hand-edit it if `terraform state` commands are inconvenient."** [State File Anatomy](/terraform-gcp/en/terraform-internals/state-file-anatomy/) proves state is versioned and enforced: a real `terraform state push` with a stale `serial` or a mismatched `lineage` is refused outright with the real error text, not silently merged.
- **"A saved plan file is basically the same as the human-readable `plan` output, just cached."** [Plan File and JSON Output](/terraform-gcp/en/terraform-internals/plan-file-and-json-output/) proves `-out` produces a real zip archive (`unzip -l` shown live) containing the plan, prior state, post-refresh state, and a full config snapshot — enough for `apply` to proceed with zero re-evaluation of your `.tf` files.
- **"Terraform 'just knows' how to talk to AWS, Azure, and GCP built in."** [Provider Plugin Protocol](/terraform-gcp/en/terraform-internals/provider-plugin-protocol/) proves every provider is a separate subprocess Terraform starts and speaks gRPC to over a Unix socket, with a real, visible `GetProviderSchema` call captured under `TF_LOG=TRACE`.
- **"`terragrunt run --all` walks units in the order `find` lists them."** [Terragrunt Discovery and DAG](/terraform-gcp/en/terraform-internals/terragrunt-discovery-and-dag/) proves ordering comes from `dependency`/`dependencies` blocks forming Terragrunt's own DAG, independent of alphabetical or discovery order — proven with a real `--parallelism 1` log showing a dependency unit's `plan` completing before either of its two dependents starts.

## Reading AI-generated code

The whole point of this module is this section, five times over — one per lesson. As a preview, here is the survey-level version: a CI "policy gate" script that looks reasonable and silently checks nothing.

<SpotTheBug code={`#!/usr/bin/env bash
# A teammate's "policy gate" before terraform apply in CI
terraform plan -out=tfplan > plan_output.txt
if grep -q "Plan: 0 to add, 0 to change, 0 to destroy" plan_output.txt; then
  echo "no changes, skipping approval"
else
  echo "changes detected, needs approval"
fi
terraform apply tfplan`}>
This greps the human-readable summary line, which is a localization- and formatting-fragile string, not a stable interface — Terraform has never documented that exact text as an API. [Plan File and JSON Output](/terraform-gcp/en/terraform-internals/plan-file-and-json-output/) proves the real, stable interface is `terraform show -json tfplan`, which exposes `resource_changes[].change.actions` as a real array (`["no-op"]`, `["create"]`, `["update"]`, `["delete","create"]`, `["forget"]`, ...) meant exactly for this use case — and `terraform plan -detailed-exitcode` (proven in the same lesson: exit code `2` for "changes present", `0` for "no changes", `1` for a real error) replaces the whole grep with a documented exit code the script can branch on directly, with no text parsing at all.
</SpotTheBug>
